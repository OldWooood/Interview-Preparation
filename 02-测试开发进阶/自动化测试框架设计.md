> 面试中"介绍一下你设计的自动化测试框架"是最能拉开差距的问题。
> 平庸回答：我用 Selenium + pytest，PO 模式，数据驱动。
> 工程回答：**分层架构 + 选型理由 + 稳定性治理 + 量化收益**。
> 本文覆盖：框架分层、pytest 进阶、接口/UI 框架落地、Flaky 治理、并发执行、工程化。

## 一、从脚本到框架：能力演进的四个阶段

| 阶段 | 形态 | 问题 |
| --- | --- | --- |
| L1 脚本 | 单个 .py 文件堆用例 | 无法维护、无法复用 |
| L2 工具类 | 封装 requests/driver | 用例之间强耦合 |
| L3 框架 | 分层 + 配置 + 报告 | 换项目要重写 |
| L4 平台 | Web 编排 + 调度 + 度量 | 建设成本高，需要持续运营 |

面试策略：**先讲分层，再讲每层的设计决策，最后讲稳定性与收益。**

## 二、标准四层架构

```
┌─────────────────────────────────────────────┐
│ 用例层（Test Cases）                          │
│ 只写业务语义：test_create_order_success()     │
│ 数据驱动：YAML / Excel / JSON / 参数化         │
├─────────────────────────────────────────────┤
│ 服务层（Business/Service Layer）              │
│ 业务动作封装：login()、create_order()          │
│ 单个接口封装 / 多接口业务编排                    │
├─────────────────────────────────────────────┤
│ 通用组件层（Common Components）                │
│ 配置管理 / 断言引擎 / 数据工厂 / 日志 / 报告     │
│ 提取器 / 数据库工具 / Mock / 加密工具           │
├─────────────────────────────────────────────┤
│ 驱动层（Driver Adapter）                      │
│ requests / httpx / grpc / Selenium / Appium  │
│ 统一 Client 接口，屏蔽底层协议差异               │
└─────────────────────────────────────────────┘
```

### 2.1 为什么这样分层？

- **用例可读**：业务人员能看懂用例在测什么；
- **变更隔离**：接口改字段只改服务层；换协议只改驱动层；
- **可复用**：登录、下单等高频动作沉淀为服务层方法；
- **可测试**：组件层可以单独单测。

### 2.2 目录结构示例


## 三、pytest 进阶（Python 系必考）

### 3.1 fixture：依赖注入 + 生命周期

**核心概念：** fixture 是被 `@pytest.fixture` 装饰的函数，测试函数通过参数名"声明依赖"，pytest 自动注入。

```python
import pytest

@pytest.fixture(scope="session")
def api_client():
    """整个测试会话只登录一次"""
    client = ApiClient()
    client.login("tester", "password")
    yield client          # yield 之前是 setup，之后是 teardown
    client.logout()

@pytest.fixture(scope="function")
def order_data(api_client):
    """每条用例独立数据，用完即删"""
    order = api_client.create_order()
    yield order
    api_client.delete_order(order["id"])
```

**scope 生命周期：**

| scope | 执行次数 | 适用场景 |
| --- | --- | --- |
| function | 每条用例 | 数据隔离（默认） |
| class | 每个类 | 类内共享前置 |
| module | 每个模块 | 模块级资源 |
| package | 每个包 | 大模块共享 |
| session | 整个会话 | 登录态、DB 连接、服务启动 |

**高频追问：**

1. **fixture 和 setup/teardown 的区别？**
   - fixture 是依赖注入，按需触发，支持组合和不同作用域；setup/teardown 是固定顺序，无法细粒度控制依赖。
2. **autouse 的陷阱？** 隐式依赖会降低可读性，测试顺序变得不可预测，慎用。
3. **fixture 之间可以依赖吗？** 可以，形成依赖树，pytest 保证正确顺序并自动去重。
4. **conftest.py 的作用域？** 该目录及子目录可见，无需 import，就近生效。

### 3.5 Hook：框架级扩展

```python
# conftest.py
def pytest_addoption(parser):
    parser.addoption("--env", default="test", help="运行环境")

def pytest_collection_modifyitems(config, items):
    """按标记排序：p0 优先执行"""
    items.sort(key=lambda i: 0 if "p0" in i.keywords else 1)

def pytest_configure(config):
    config.addinivalue_line("markers", "smoke: 冒烟用例")

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """失败自动截图（UI 场景）"""
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed:
        driver = item.funcargs.get("driver")
        if driver:
            driver.save_screenshot(f"reports/{item.name}.png")
```

### 3.6 断言与软断言

```python
# 硬断言：失败立即终止
assert resp.status_code == 200

# 软断言：收集所有失败再统一报告（pytest-assume）
from pytest import assume
assume(resp.status_code == 200)
assume(resp.json()["data"]["amount"] == 100)
```

**接口断言引擎设计要点：**

```python
class AssertEngine:
    def assert_status(self, resp, expected): ...
    def assert_json_schema(self, resp, schema): ...       # jsonschema 校验结构
    def assert_field(self, resp, jsonpath, expected): ... # 字段级断言
    def assert_contains(self, resp, text): ...
    def assert_db(self, sql, expected): ...               # 数据库落库校验
```

### 4.2 客户端封装示例

```python
import requests
from tenacity import retry, stop_after_attempt, wait_exponential

class ApiClient:
    def __init__(self, base_url, timeout=10):
        self.base_url = base_url
        self.session = requests.Session()
        self.timeout = timeout

    def _request(self, method, path, **kwargs):
        url = self.base_url + path
        kwargs.setdefault("timeout", self.timeout)
        resp = self.session.request(method, url, **kwargs)
        self._log(method, url, kwargs, resp)
        return resp

    @retry(stop=stop_after_attempt(3), wait=wait_exponential(min=1, max=5))
    def request(self, method, path, **kwargs):
        return self._request(method, path, **kwargs)

    def _log(self, method, url, kwargs, resp):
        ...  # 记录请求/响应，敏感字段脱敏
```

### 4.4 面试题：接口关联怎么处理？

> 上游接口的返回值作为下游接口的入参。

方案：
1. **上下文对象**：全局上下文（dict）存变量，用例内引用 `${token}`；
2. **提取器**：从响应中按 jsonpath/正则提取并写入上下文；
3. **数据依赖图**：复杂场景用 DAG 编排（pytest 里用 fixture 依赖或自定义编排引擎）。

```python
class Context:
    _data = {}
    @classmethod
    def set(cls, key, value): cls._data[key] = value
    @classmethod
    def get(cls, key): return cls._data.get(key)
```

**POM 面试追问：**

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 POM？ | 页面元素与用例分离，一处修改全局生效 |
| PO 与组件化区别？ | 大页面拆成组件对象（弹窗、表格、导航），避免"超级 PO 类" |
| 要不要在 PO 里写断言？ | 业务断言放用例层；PO 只提供状态查询方法 |
| 定位器放哪？ | 集中管理（类属性/YAML），便于自愈和统一维护 |

### 5.2 等待机制（高频）

| 方式 | 说明 | 评价 |
| --- | --- | --- |
| 强制等待 sleep | 固定等待 | ❌ 不稳定且浪费时间 |
| 隐式等待 | 全局等待元素出现 | ⚠️ 与显式等待混用有坑 |
| 显式等待 | 等待条件满足 | ✅ Selenium 推荐 |
| Playwright 自动等待 | 操作前自动等待可操作性 | ✅ 首选 |

```python
# Selenium 显式等待
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

WebDriverWait(driver, 10).until(
    EC.element_to_be_clickable((By.ID, "submit"))
).click()
```

```python
# Playwright 自动等待 + 断言
from playwright.sync_api import expect
page.get_by_role("button", name="提交").click()
expect(page.get_by_text("提交成功")).to_be_visible()
```

### 5.3 定位策略优先级（Playwright / 现代 Web）

```
1. data-testid（与前端约定，稳定）  ← 最推荐
2. 语义定位 get_by_role / get_by_label
3. 文本定位 get_by_text
4. CSS 选择器
5. XPath（最后手段，性能差、脆弱）
```

**面试题：CSS 与 XPath 怎么选？**

- CSS 更快、语法简洁，适合层级/属性定位；
- XPath 支持文本、轴定位（父级/兄弟），适合复杂场景；
- 现代框架优先语义定位，避免依赖易变的 DOM 层级。

### 5.4 失败处理

- 失败自动截图 + 页面源码 + 控制台日志 + 网络请求（Playwright Trace）;
- 重试策略：只重试已知 Flaky 用例，次数 ≤ 2，记录原因；
- 环境快照：Docker 固定浏览器版本。

## 六、Flaky 用例治理（必考）

### 6.1 什么是 Flaky

同一条用例、同一份代码，多次执行结果不一致（时过时不过）。

**危害：** 团队失去对自动化的信任 → 不再看失败报告 → 门禁形同虚设。

### 6.2 分类与根因

| 类型 | 典型根因 | 解决方案 |
| --- | --- | --- |
| 环境问题 | 服务不稳定、依赖的第三方波动 | Docker/环境隔离、Mock 外部依赖 |
| 数据问题 | 数据被并发修改、脏数据 | 数据工厂、独立测试数据、幂等清理 |
| 时序问题 | 等待不充分、异步未同步 | 条件等待、监听接口响应 |
| 用例耦合 | 用例间共享状态、执行顺序依赖 | 用例独立、autouse 清理 |
| 定位器脆弱 | UI 改动、动态 ID | data-testid、语义定位、自愈 |
| 资源竞争 | 并发抢占、端口冲突 | 资源池、动态端口、串行化关键用例 |

### 6.3 定位方法

```bash
# pytest 自带失败重跑统计
pytest --reruns 5 -p no:randomly -q

# 或用 pytest-flaky / 自研插件记录执行矩阵
```

**工程做法：**

1. 记录每条用例的最近 N 次执行结果，计算 **通过率**；
2. 通过率 < 95% 自动标记为 `quarantine`（隔离区），不阻塞门禁；
3. 周会专项治理 Flaky，看板展示 Top 10 不稳定用例；
4. 禁止用"无脑重试"掩盖真实缺陷——重试通过也记录一次 Flaky 事件。

### 6.4 面试回答模板

> 我会分层排查：先看环境（是否固定镜像/固定依赖），再看数据（是否隔离和可回收），再看用例逻辑（是否依赖外部状态），最后看框架等待机制。对网络波动等不可控因素引入自动重试，但**重试不超过两次且记录原因**；同时建立稳定性大盘，目标是冒烟用例稳定性 ≥ 99%，不达标用例进隔离区专项治理。

## 七、并发与分布式执行

### 7.1 pytest-xdist

```bash
# -n auto：按 CPU 核数并发；--dist loadscope：按模块分组减少冲突
pytest -n 4 --dist loadscope
```

**并发带来的问题：**

- 共享测试数据相互污染 → 数据必须按 worker 隔离（`worker_id`）；
- 登录态等 session 级 fixture 会在每个 worker 执行一次；
- 非线程安全的库（部分 SDK）需要每 worker 独立初始化。

```python
@pytest.fixture(scope="session")
def worker_id(request):
    return getattr(request.config, "workerinput", {}).get("workerid", "master")
```

### 7.2 分布式架构

```
调度中心（Jenkins / 自研平台）
        │  分发任务
   ┌────┼────┐
 执行机A 执行机B 执行机C   ← Docker 容器 / K8s Job
   │    │    │
   └────┴────┘
        │  上报结果
   结果聚合 + Allure 报告
```

- **执行机即用即毁**：Docker 镜像内含浏览器/驱动/依赖，保证环境一致；
- **K8s 动态 Pod**：Jenkins kubernetes-plugin 按需创建 Agent；
- **用例分片**：按历史耗时均衡分发（bin packing），避免长尾。

   - 为什么接口优先于 UI：稳定性、执行速度、性价比；
   - 数据驱动 + 环境隔离方案；
4. 稳定性治理：Flaky 大盘、隔离区、重试策略；
5. 收益：回归时间 X→Y、稳定性、缺陷拦截、维护成本。

### Q2：自动化用例不稳定怎么办？

见本文第六节，回答要点：分类排查 + 数据隔离 + 重试上限 + 稳定性指标 + 禁止掩盖问题。

### Q3：自动化测试什么时候做？投入产出怎么算？

- 时机：需求稳定后、接口联调完成后开始接口自动化；UI 只覆盖核心链路；
- ROI：`收益 =（手工耗时 - 自动化耗时）× 执行频次 - 建设成本 - 维护成本`；
- 高频回归、核心链路、跨版本稳定功能优先，探索期业务不投入。

### Q4：pytest fixture 和 unittest setUp 的区别？

见 3.1 追问。

### Q5：如何保证自动化用例本身的质量？

- 用例评审（自动化用例也要评审）；
- 用例独立、可重复执行；
- 定期跑"用例有效性"验证（变异测试/注入缺陷）；
- 覆盖率与缺陷拦截率作为效果指标，而不是用例数量。
