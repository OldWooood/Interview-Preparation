# 🏛️ 测试平台系统设计题（高级测试开发面试）

> 高级岗位/专家岗必考："设计一个 XX 平台"。
> 考察的不是画图能力，而是：**需求拆解 → 架构分层 → 核心机制 → 技术选型 → 可扩展性与数据闭环**。

---

## 一、通用答题框架（背熟）

```
1. 需求澄清（1 分钟）
   - 用户是谁？（测试/开发/产品）
   - 解决什么问题？规模多大？（用户数、用例量、日执行量）
   - 边界是什么？（不做什么）
2. 总体架构（3 分钟）
   - 分层：接入层 / 业务层 / 调度层 / 执行层 / 数据层
   - 画架构图（一定要说出来）
3. 核心模块设计（5 分钟）
   - 数据模型（表结构）
   - 关键流程（用例编写 → 调度 → 执行 → 报告 → 通知）
   - 难点与解决（并发、隔离、幂等、性能）
4. 技术选型与理由（2 分钟）
   - 后端语言、框架、DB、缓存、队列、调度
5. 可扩展性与演进（1 分钟）
   - 插件化、多协议、开放 API、AI 能力接入
```

### 通用技术选型参考

| 组件 | 选项 | 选择理由 |
| --- | --- | --- |
| 后端 | Spring Boot（Java）/ Django/FastAPI（Python） | Java：稳定、团队主栈；Python：开发快 |
| 前端 | Vue / React | 组件化、生态好 |
| 数据库 | MySQL | 结构化数据 |
| 缓存 | Redis | 会话、分布式锁、热点配置 |
| 消息队列 | Kafka/RabbitMQ/RocketMQ | 任务异步、削峰 |
| 调度 | XXL-Job（Java）/ Celery（Python）/ K8s CronJob | 分布式调度、重试、监控 |
| 执行器 | Docker 容器 / K8s Job / Agent | 隔离、弹性 |
| 存储 | 对象存储（OSS/S3） | 报告、截图、附件 |
| 监控 | Prometheus + Grafana | 平台自身可观测 |

## 二、设计一个测试用例管理平台

### 2.1 需求与用户

| 角色 | 需求 |
| --- | --- |
| 测试工程师 | 编写/组织/执行用例、导入导出、统计 |
| 测试负责人 | 评审、任务分配、覆盖率与质量报表 |
| 开发/产品 | 查看用例、追溯需求、参与评审 |

### 2.2 核心功能

```
用户与权限（RBAC）
用例管理：增删改查、分组（模块/版本）、标签、批量操作
导入导出：Excel、XMind、思维导图、API
关联：需求（Jira/TAPD）、缺陷、自动化脚本、执行记录
评审流：草稿 → 评审中 → 通过/驳回（状态机）
测试计划/任务：选择用例集 → 分配执行人 → 进度跟踪
执行记录：手工结果（通过/失败/阻塞）+ 缺陷链接
统计：覆盖率、通过率、缺陷密度、趋势
```

### 2.3 数据模型（关键表）

```sql
-- 用例主表
CREATE TABLE test_case (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(255) NOT NULL,
  project_id BIGINT,
  module_id BIGINT,
  priority ENUM('P0','P1','P2','P3'),
  type ENUM('FUNCTION','API','UI','PERFORMANCE'),
  precondition TEXT,
  steps JSON,               -- [{action, expected}]
  status ENUM('DRAFT','REVIEWING','APPROVED','DEPRECATED'),
  author_id BIGINT,
  version INT DEFAULT 1,
  created_at DATETIME,
  updated_at DATETIME
);

-- 用例-需求关联（多对多）
CREATE TABLE case_requirement (
  case_id BIGINT, requirement_id BIGINT,
  PRIMARY KEY (case_id, requirement_id)
);

-- 测试计划
CREATE TABLE test_plan (
  id BIGINT PRIMARY KEY,
  name VARCHAR(255),
  version VARCHAR(64),
  start_at DATETIME, end_at DATETIME,
  owner_id BIGINT, status VARCHAR(32)
);

-- 执行记录
CREATE TABLE case_execution (
  id BIGINT PRIMARY KEY,
  plan_id BIGINT, case_id BIGINT,
  executor_id BIGINT,
  result ENUM('PASS','FAIL','BLOCK','SKIP'),
  bug_id BIGINT NULL,
  remark TEXT,
  executed_at DATETIME
);
```

### 2.4 难点与设计

| 难点 | 方案 |
| --- | --- |
| 用例与需求追溯 | 多对多关联表 + 覆盖率计算 |
| 版本管理 | 用例快照（执行时冻结版本） |
| 评审流程 | 状态机 + 操作日志 |
| 大规模导入 | 异步任务 + 分批入库 + 进度通知 |
| 权限 | RBAC 模型（用户-角色-权限），项目隔离 |
| 统计性能 | 预聚合 + 定时任务写汇总表（避免实时全表扫） |

## 三、设计一个接口自动化平台

### 3.1 架构图

```
┌────────────────────────────────────────────────┐
│ 展现层：Web（用例编排 / 任务触发 / 报告查看）        │
├────────────────────────────────────────────────┤
│ 接入层：API 网关（鉴权 / 限流）                    │
├────────────────────────────────────────────────┤
│ 业务层：用例管理 / 场景编排 / 环境管理 / 报告服务     │
├────────────────────────────────────────────────┤
│ 调度层：任务队列（MQ）+ 调度器（XXL-Job/Celery）     │
├────────────────────────────────────────────────┤
│ 执行层：执行引擎（解析 DSL → 驱动 HTTP/RPC）        │
│        Executor 集群 / K8s Job / Agent           │
├────────────────────────────────────────────────┤
│ 数据层：MySQL（元数据）+ Redis（缓存/锁）           │
│        OSS（报告附件）+ ES（日志检索）              │
└────────────────────────────────────────────────┘
```

### 3.2 用例编写三种模式

| 模式 | 用户 | 说明 |
| --- | --- | --- |
| 表单化 | 功能测试 | 页面配置接口、参数、断言 |
| YAML/JSON DSL | 测试开发 | 文件式，Git 管理 |
| 代码模式 | 测试开发 | Python/Java 脚本，灵活 |

**DSL 设计示例：**

```yaml
name: 下单支付流程
variables:
  user: ${env.test_user}
steps:
  - name: 登录
    request:
      method: POST
      url: /api/login
      json: {username: "${user}", password: "123456"}
    extract:
      token: $.data.token
    validate:
      - eq: [status_code, 200]
      - jsonpath: [$.code, 0]

  - name: 创建订单
    request:
      method: POST
      url: /api/order
      headers: {Authorization: "Bearer ${token}"}
      json: {skuId: 1001, count: 1}
    extract:
      order_id: $.data.orderId
    validate:
      - jsonpath: [$.data.status, "CREATED"]

  - name: 数据库校验
    db:
      sql: "SELECT status FROM orders WHERE id = ${order_id}"
      expected: [[PAID]]
```

### 3.3 执行引擎设计

```
任务下发 → 执行机拉取任务（或 MQ 推送）
→ 解析用例（DSL → 执行树）
→ 建立上下文（变量池）
→ 逐步执行 + 提取变量 + 断言
→ 失败处理（继续/终止/重试）
→ 汇聚结果 → 生成报告 → 通知
```

**关键机制：**

| 机制 | 说明 |
| --- | --- |
| 变量池 | 环境变量、全局变量、用例变量、步骤提取变量 |
| 断言引擎 | 状态码/JSONPath/JSON Schema/DB/脚本断言 |
| 前置后置 | 脚本 Hook、数据库脚本、清理任务 |
| 重试 | 仅幂等步骤重试，退避策略 |
| 超时 | 步骤级 + 任务级超时，防卡死 |
| 并发 | 用例间并行、步骤内串行；资源隔离 |
| 幂等 | 任务去重键（用例集+环境+提交版本） |

### 3.4 报告与度量

- 结果：通过/失败/错误/跳过，失败原因分类；
- 详情：请求/响应/耗时/断言差异/关联日志；
- 趋势：通过率曲线、失败 Top、耗时分布；
- 度量：自动化覆盖率、稳定性、节省人力。

### 3.5 高频追问

| 追问 | 回答要点 |
| --- | --- |
| 怎么支持多环境？ | 环境配置独立存储，运行时注入变量，禁止硬编码 |
| 怎么保证执行机隔离？ | 每次任务独立容器，或按项目隔离 Agent 池 |
| 用例依赖怎么处理？ | 优先用例独立；跨用例依赖用场景编排显式声明 |
| 支持 gRPC/Dubbo 吗？ | 插件化协议适配器，统一抽象 Request/Response |
| 怎么防滥用？ | 限流、权限、生产环境禁写、审批 |

## 四、设计一个 Mock 平台

### 4.1 核心需求

- 前后端联调：接口未就绪时返回 Mock 数据；
- 异常测试：模拟超时、错误码、慢响应；
- 第三方依赖隔离：稳定可用的虚拟服务。

### 4.2 架构

```
客户端 → DNS/Hosts/代理配置 → Mock Server（匹配规则）
                                    ├─ 命中 → 返回 Mock 响应
                                    └─ 未命中 → 转发真实服务（可录制）
```

### 4.3 匹配规则设计

```yaml
rules:
  - match:
      method: POST
      path: /api/pay
      query: {channel: "wechat"}
      headers: {app-version: ">=8.0"}
      body_contains: "orderId"
    response:
      delay_ms: 3000
      status: 500
      json:
        code: 50001
        message: "支付网关超时"
    scope: {env: [test], user: [zhangsan]}
```

| 规则维度 | 说明 |
| --- | --- |
| 匹配 | 路径、方法、query、header、body 关键字 |
| 响应 | 状态码、头、静态 JSON、动态模板、脚本 |
| 行为 | 延迟、超时、断连、循环返回多个响应 |
| 生效范围 | 环境/用户/App 版本/时间窗口 |
| 优先级 | 精确匹配 > 模糊匹配，可手动调整 |

### 4.4 难点

| 难点 | 方案 |
| --- | --- |
| HTTPS 解密 | CA 证书 + 代理（mitmproxy） |
| 移动端接入 | 证书安装引导、VPN/WiFi 代理配置 |
| 规则冲突 | 优先级 + 冲突检测 + 命中日志 |
| 动态响应 | 模板引擎（Mock.js/JS/Python 沙箱） |
| 性能 | 本地 Agent 代理，减少中心服务压力 |
| 安全 | 沙箱执行、规则权限隔离 |

## 五、设计一个造数平台

### 5.1 核心概念

```
数据模板（定义数据结构与生成规则）
  + 变量池（可复用参数）
  + 执行器（SQL/HTTP/MQ/脚本）
  + 数据池（生成后的数据存储与回收）
```

### 5.2 架构

```
Web 配置 → 模板解析 → 执行引擎（DAG 编排）
   ├─ SQL 执行器（MySQL/ClickHouse）
   ├─ HTTP 执行器（调用内部造数接口）
   ├─ MQ 生产者（模拟上游消息）
   └─ 脚本执行器（Groovy/Python，自定义逻辑）
→ 数据池（分配/回收/重置）→ 对外 API（自动化框架调用）
```

### 5.3 数据模型

```yaml
template: 电商订单
steps:
  - id: create_user
    type: sql
    sql: "INSERT INTO users(name, phone) VALUES('${name}', '${phone}')"
    output: user_id
  - id: create_order
    type: http
    request: {method: POST, url: "/test-api/order", json: {userId: "${user_id}"}}
    output: order_id
variables:
  name: "压测用户_${random(8)}"
  phone: "138${random_digits(8)}"
cleanup:
  - "DELETE FROM orders WHERE id = '${order_id}'"
  - "DELETE FROM users WHERE id = '${user_id}'"
```

### 5.4 难点

| 难点 | 方案 |
| --- | --- |
| 数据一致性 | 事务/最终一致补偿、外键顺序 |
| 幂等 | 数据唯一标识、重复检测 |
| 回收 | 引用计数、TTL 自动清理、手工回收 |
| 大批量 | 批量插入、异步任务、分批限速 |
| 环境隔离 | 按环境路由数据源 |
| 安全 | 禁止生产写、SQL 白名单审计 |

## 六、设计一个流量回放平台

### 6.1 架构（详见接口专题，此处为平台视角）

```
① 采集层：Java Agent（字节码增强）/ 网络抓包 / 日志采集
② 存储层：MQ 削峰 → 明细存储（HBase/ES）+ 元数据（MySQL）
③ 处理层：清洗、去重、采样、脱敏、标签化
④ 回放层：调度 → 回放引擎 → 目标环境（预发/新版本）
⑤ 对比层：Diff 引擎（字段级 + 容差 + 忽略规则）→ 差异报告
⑥ 应用层：回归任务、Bug 验证、压测造流量、数据构造
```

### 6.2 关键设计

| 设计点 | 方案 |
| --- | --- |
| 无侵入采集 | Agent attach，动态字节码增强（jvm-sandbox） |
| 去重 | 按接口 + 参数特征哈希去重，保留多场景 |
| 写流量 | 开关关闭 / Mock 下游 / 影子库 |
| 时间一致性 | 时间 Mock（替换 System.currentTimeMillis） |
| Diff 治理 | 忽略字段、容差、结构化比对、对比策略配置 |
| 覆盖率 | 回放时采集 JaCoCo 覆盖率，报告未覆盖分支 |
| 限流 | 回放速率限制，避免压垮目标环境 |

### 6.3 面试验证点

- 怎么保证回放不影响线上？→ 只读接口 + 限流 + 白名单；
- 大量 Diff 怎么分析？→ 分类聚类 + 已知规则沉淀 + 只看业务字段；
- 怎么评估回放价值？→ 覆盖接口数、Diff 发现问题数、替代人工回归时长。

## 七、设计一个精准测试平台

### 7.1 架构

```
代码仓库（Git Diff）
    │
    ▼
① 分析层：AST 解析 → 方法调用链（静态）+ Trace（动态）
    │
    ▼
② 知识库：方法 ↔ 接口 ↔ 用例 映射（倒排索引）
    │
    ▼
③ 推荐层：变更方法 → 变更接口 → 影响接口 → 用例召回 → 排序去重
    │
    ▼
④ 执行层：触发自动化回归 → 采集覆盖率
    │
    ▼
⑤ 度量层：精准率、漏测率、覆盖率、提效数据
```

### 7.2 核心技术

| 技术 | 用途 |
| --- | --- |
| AST（javaparser/tree-sitter） | 代码解析、方法级 Diff |
| 调用链分析 | 静态（代码） + 动态（Trace）结合 |
| JaCoCo | 用例执行覆盖率采集 |
| 倒排索引 | 方法/代码块 → 用例快速召回 |
| 字节码增强 | 运行时跟踪方法调用 |
| 排序模型 | 按变更相关度、业务热度、历史缺陷排序 |

### 7.3 度量指标

```
精准率 = 推荐变更接口数 / 实际变更接口数
漏测率 = 未推荐且实际变更的接口数 / 实际变更接口数
提效 = 1 - 精准回归用例数 / 全量用例数
```

## 八、设计一个质量度量平台（大盘）

### 8.1 数据来源

| 数据 | 来源 |
| --- | --- |
| 缺陷数据 | Jira/TAPD API |
| 测试执行 | 自动化平台、用例平台 |
| 代码质量 | SonarQube、覆盖率平台 |
| 发布数据 | CI/CD 平台 |
| 线上质量 | 监控系统、故障平台 |
| 效能数据 | DevOps 平台 |

### 8.2 指标建模

```
事实表（明细）+ 维度表（项目/团队/时间/服务）
→ 定时聚合任务 → 汇总表 → 可视化大盘
```

### 8.3 难点

- 数据口径统一（什么是"缺陷逃逸"）；
- 实时性 vs 性能（预聚合）；
- 指标归因与下钻（从大盘到服务到人）；
- 避免指标游戏（见质量体系文档）。

## 九、面试实战：完整示例回答

**题目：设计一个接口自动化测试平台（面向 500 人研发团队）**

```
【澄清】用户：测试与开发；规模：日执行 10 万条用例；约束：支持 HTTP/gRPC，
生产环境只读；核心诉求：降低自动化门槛、统一执行、质量度量。

【架构】五层：Web 展现 → API 网关 → 业务服务 → 调度 → 执行器 → 数据层。

【核心模块】
- 用例：表单/YAML/代码三种模式，Git 集成；
- 环境：环境配置中心，变量注入；
- 执行：MQ + XXL-Job 调度，K8s Job 执行，步骤级超时重试；
- 报告：Allure 风格详情 + 趋势大盘；
- 通知：飞书/钉钉机器人，@责任人。

【数据模型】项目、环境、用例、用例集、任务、执行记录、步骤结果、变量。

【技术选型】Spring Boot + MySQL + Redis + RocketMQ + XXL-Job + K8s，
报告存 OSS，检索用 ES；理由：团队 Java 栈、稳定、生态成熟。

【难点】并发执行隔离（容器化）、用例依赖（场景编排 DAG）、
数据污染（数据工厂+清理）、大规模报告存储（OSS+异步生成）。

【演进】支持流量回放联动、精准测试推荐、AI 用例生成，
开放 OpenAPI 供外部系统集成。
```

## 十一、总结

> 平台设计答题 = **需求澄清 + 分层架构 + 数据模型 + 核心机制 + 选型理由 + 演进路线**。
> 永远主动讲"难点和 trade-off"，这是高级岗位和普通岗位的分水岭。
