## 第一轮：性能理论

### Q1 ⭐ 你们性能测试的指标有哪些？

**答：**

- 吞吐：TPS/QPS；
- 响应时间：平均、P95、P99、最大；
- 错误率/超时率；
- 并发：并发用户数、线程数、连接数；
- 资源：CPU、内存、磁盘 IO、网络、GC、连接池；
- 业务指标：订单成功率、支付转化率。

补充一句："我们看 P95/P99 而不是平均值，因为平均值会掩盖长尾。"

🔁 追问：TPS 和 QPS 的区别？→ TPS 以事务为单位（一个事务可能多请求），QPS 以单请求计；业务系统常按核心事务统计。

🔁 追问：并发用户数和 RPS 怎么换算？→ Little's Law：并发数 = RPS × 平均响应时间。

---

### Q2 性能测试有哪些类型？

| 类型 | 目的 |
| --- | --- |
| 基准测试 | 建立单接口基线 |
| 负载测试 | 预期负载下验证指标 |
| 压力测试 | 阶梯加压找拐点/极限 |
| 稳定性测试 | 长时间验证资源泄漏 |
| 峰值/尖峰测试 | 大促瞬时流量 |
| 全链路压测 | 端到端容量评估 |

### Q3 ⭐ 性能测试什么时候做？

**参考话术：**

> 永远不要等最后做。三个时机：
> ① 技术方案评审阶段介入，识别性能和容量风险，明确目标；
> ② 接口提测后做单接口基准，早期发现 N+1 查询、慢 SQL 这类低级问题；
> ③ 核心功能稳定后做全链路压测和长稳，评估总容量。
> 越晚发现修复成本越高。

### Q4 ⭐ 性能测试场景怎么设计？

**答：**

> 不拍脑袋，基于线上流量模型：分析生产日志，提取核心链路的接口调用比例、参数分布、思考时间；按比例混合压测；同时设计摸高场景（找极限）和稳定性场景（7×24 找泄漏）。
> 数据准备要贴近真实分布（用户数、商品数、热点集中度），避免全冷数据测出假指标。

🔁 追问：5000 人抢 50 个库存，怎么设计并发？→ 这不是纯性能问题：并发模拟 5000 人同时请求，验证超卖与锁；再加更高并发找系统极限；区分"业务并发"与"系统并发"。

### Q5 阈值/预期指标怎么定？

**答：** 参考三个来源：SLA（如 P95 ≤ 200ms）、历史基线（上一版本对比）、业务容忍度（用户可接受的等待）。大促按目标 TPS × 安全系数（1.5–2 倍）压测，留冗余。

## 第二轮：压测实施

### Q6 JMeter、K6、Locust 怎么选？

| 工具 | 特点 | 适用 |
| --- | --- | --- |
| JMeter | 成熟、插件多、GUI | 传统压测、复杂协议 |
| K6 | JS 脚本、CI 友好、指标导出 | 工程化、云原生 |
| Locust | Python、易扩展 | 定制逻辑、团队 Python 栈 |
| wrk | 轻量高并发 | 单纯打 RPS |

回答技巧："选型看协议支持、脚本能力、CI 集成和团队栈，不迷信单一工具。"

### Q7 压测环境怎么准备？

**答：** 尽量贴近生产：同规格机器、同版本服务、同配置；数据量与分布贴近；第三方依赖 Mock 或影子；压测机与被测服务隔离（避免互相干扰）；监控全链路就绪（系统/应用/中间件/链路追踪）。

🔁 追问：压测数据怎么隔离？→ 影子库/影子表、流量标识走隔离逻辑、独立环境；避免污染生产数据。

### Q8 分布式压测怎么做？

**答：** JMeter Master-Slave 或 K8s 容器化发压机，注意：发压机自身不能成为瓶颈（CPU/网络）；多机器时钟同步；结果聚合；脚本与参数文件分发；目标服务入口带宽评估。

## 第三轮：瓶颈定位（核心）

### Q9 ⭐⭐ 压测中 TPS 上不去，你怎么排查？

**参考话术（按层排查）：**

```
1. 先看现象：RT 升高还是错误率升高？发生在哪个阶段（爬上/稳态）？
2. 发压侧：压测机瓶颈？带宽？连接数？脚本逻辑（等待/断言耗时）？
3. 网络：延迟、丢包、DNS、网关/QPS 限流
4. 应用：CPU（us/sy）、GC（Full GC 频率/停顿）、线程池/连接池是否打满、锁竞争
5. 数据库：慢 SQL、锁等待、连接数、IO
6. 缓存/MQ：命中率、大 key、积压
7. 下游依赖：RT 与错误率
8. 链路追踪：找最慢 Span，逐层下钻
```

**工具：** top/vmstat/iostat、jstack/jmap/GC 日志/Arthas、慢查询日志、SkyWalking/Jaeger、Prometheus/Grafana。

🔁 追问：CPU 高但 TPS 低可能是什么？→ 锁竞争、频繁 GC、大量上下文切换、加密运算、正则回溯、死循环。

🔁 追问：内存不涨但频繁 GC？→ 对象分配速率过高（小对象多）、堆太小、缓存不合理。

---

### Q10 一个接口平均 RT 200ms，P99 2s，怎么定位？

**答：** 先看 P99 的时间分布（哪些请求慢）：是特定参数（大分页/大 key）、特定实例（热点/GC）、特定时段（定时任务/Cache 失效）、还是下游偶发。用 Trace + 日志采样定位慢请求的共同特征，再针对性优化。

### Q11 数据库是瓶颈，常见优化有哪些？

**答：** 索引优化（覆盖索引/最左前缀）、SQL 改写（避免 SELECT *、深分页优化）、读写分离、缓存热点、连接池调优、分库分表、归档冷数据。快速验证：加索引后重压对比。

### Q12 缓存相关性能问题有哪些？

**答：** 缓存击穿（热点到期）导致 DB 瞬时高压；大 key 导致网络阻塞；热 key 单节点打满；缓存与 DB 不一致导致重试风暴。压测时要专门构造热 key、大 key、批量失效场景。

### Q13 全链路压测怎么做？

**参考话术：**

> ① 梳理链路与容量目标；② 数据隔离方案（影子库/流量标识）；③ 脚本编排（各服务按比例）；④ 监控与告警就绪；⑤ 阶梯加压 → 稳态保持 → 观测；⑥ 瓶颈定位与优化 → 复压验证；⑦ 输出容量报告和扩容建议。
> 大促前还会做"全链路压测 + 故障注入"组合，验证熔断降级真实可用。

## 第四轮：稳定性与混沌工程

### Q14 ⭐ 什么是混沌工程？

**参考话术：**

> 混沌工程是在系统上做受控实验，主动注入故障，验证系统在异常条件下的行为是否符合预期。
> 五条原则：定义稳态指标、模拟真实故障、尽量在生产做、持续自动化、控制爆炸半径。
> 和测试的区别：测试验证已知输入输出，混沌探索未知的失败行为。它不是随机破坏，而是有假设、有监控、有止损的科学实验。

🔁 追问：工具用过哪些？→ ChaosBlade（场景多、无 K8s 依赖）、Chaos Mesh（K8s CRD、编排强）、LitmusChaos；命令示例：`blade create network delay --time 3000`、`blade create jvm throwCustomException`。

### Q15 ⭐ 你会给订单系统设计一次混沌演练吗？

**参考话术（完整示例）：**

> **目标**：验证下单链路在支付依赖超时时的韧性。
> **稳态指标**：下单成功率 ≥ 99.9%，支付回调延迟 < 5s，无重复扣款。
> **假设**：支付接口延迟 3s 时熔断触发，订单进入待支付，恢复后可继续支付。
> **注入**：ChaosBlade 对支付服务网络延迟 3s，仅影响 1 个实例。
> **半径**：测试环境先验 → 生产 1% 流量、5 分钟自动恢复、业务低峰、双人复核。
> **观察**：成功率、RT、熔断次数、错误日志、订单状态。
> **结果判定与复盘**：指标不劣化视为通过；发现韧性缺口则修复并纳入常态化演练。

### Q16 混沌工程怎么控制爆炸半径？

**答：** 环境隔离（测试→预发→生产）、流量比例（1% 实例/单机房）、时间窗口（避峰值）、一键终止、白名单、监控值守、双人复核。原则：**知道系统没有容错能力时，不要做该实验**。

### Q17 演练发现了问题，后续怎么闭环？

**答：** 修复 → 补充监控告警 → 补充自动化用例 → 加入常态化演练计划（每月/流水线内）→ 复盘沉淀到故障库。目标是从"首轮注入"走到"常态化演练"，防止退化。

### Q18 长稳测试怎么做？

**答：**

> 目标：发现内存/连接/句柄/日志泄漏和性能衰减。
> 场景：核心链路混合流量跑 72 小时或 7 天，恒定压力。
> 监控：内存/GC/连接数/句柄/错误率趋势。
> 判定：指标平稳无持续增长，性能不衰减；结束后对比基线。
> 技巧：定期触发流量高峰和低谷，观察恢复能力。

## 第五轮：开放与场景

### Q19 线上 CPU 突然飙升，怎么处理？

**答：** 先止损（限流/回滚/扩容）再看根因：`top -Hp` 找高 CPU 线程 → 转 16 进制 → `jstack` 定位栈 → 区分业务高峰（正常）、死循环/正则回溯（代码问题）、频繁 GC（内存问题）、流量攻击。修复后加监控告警。

### Q20 大促前你会做哪些保障？

```
容量：全链路压测 → 瓶颈优化 → 扩容
预案：限流/降级/熔断参数核对 + 回滚演练 + 切流演练
稳定：混沌演练 + 长稳测试 + 热点隔离
监控：大盘巡检 + 告警阈值复核 + 值守排班
演练：故障演练（依赖宕机/缓存失效/MQ 积压）
```

### Q21 压测结果和线上表现不一致，为什么？

**答：** 数据分布不同（冷热）、流量模型不同（比例/思考时间）、环境差异（机器/网络/依赖 Mock）、缓存状态不同（预热）、线上有其他业务混跑。对策：尽量逼近生产、缓存预热、错峰压测、线上引流回放。
