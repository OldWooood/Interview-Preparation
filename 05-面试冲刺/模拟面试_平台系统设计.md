# 🎤 模拟面试：平台系统设计

> 覆盖：用例/接口自动化/Mock/造数/流量回放/精准测试/质量大盘/CI 流水线/环境方案。
> 对应复习文档：[测试平台系统设计题](../02-测试开发进阶/测试平台系统设计题.md)。
> 答题公式：**需求澄清 → 总体架构 → 核心模块 → 数据模型 → 技术选型 → 难点取舍 → 演进路线**。

---

## 通用开场模板（先背这段）

> "设计之前我先明确三件事：用户是谁、解决什么问题、规模多大。然后我会按五层来设计：接入层、业务层、调度层、执行层、数据层，最后讲核心模块、技术选型和扩展性。"

**追问应对原则：**

- 面试官问"为什么用 XX"→ 对比备选 + 结合团队现状；
- 面试官问"并发怎么处理"→ MQ 削峰 + 水平扩展 + 幂等；
- 面试官问"数据量大怎么办"→ 分表/归档/预聚合；
- 不确定就说"我会先小规模验证，再决定是否引入"——不要硬编复杂方案。

## Q1 ⭐⭐ 设计一个测试用例管理平台

**参考对话：**

> **澄清**：用户是测试和测试负责人；规模 200 人、10 万条用例；要支持需求追溯、评审和统计。
>
> **架构**：
> 前端 Vue/React → API 网关（鉴权/限流）→ 业务服务（用例/计划/评审/统计）→ MySQL + Redis → 异步任务（导入导出、报表）。
>
> **核心模块**：
> ① 用例管理：树形分组（项目/模块/版本）、标签、批量操作、导入导出（Excel/XMind/API）；
> ② 关联体系：用例 ↔ 需求（Jira/TAPD）、缺陷、自动化脚本，双向追溯算覆盖率；
> ③ 评审流：草稿 → 评审中 → 通过/驳回，状态机 + 操作日志；
> ④ 计划与执行：选用例集、分配执行人、记录结果、链接缺陷、生成报告；
> ⑤ 统计：覆盖率、通过率、缺陷密度、趋势。
>
> **数据模型**：test_case（含 steps JSON、status、version）、case_requirement（多对多）、test_plan、case_execution。
>
> **难点**：
> ① 版本管理：执行时冻结用例快照，避免后续修改影响历史报告；
> ② 大规模导入：异步任务 + 分批入库 + 进度通知；
> ③ 统计性能：预聚合汇总表 + 定时任务，避免实时全表扫；
> ④ 权限：RBAC + 项目隔离。
>
> **演进**：自动化用例平台联动 → 精准推荐 → AI 生成用例接入。

**追问问答：**

🔁 用例和自动化脚本怎么关联？→ 用例表存自动化标签/脚本路径，执行结果回写用例执行记录；平台间用 OpenAPI 打通。
🔁 怎么防止用例被误删？→ 软删除 + 回收站 + 操作审计，删除需权限。
🔁 覆盖率怎么算？→ 有需求的用例数/需求总数，按项目/版本维度聚合。

## Q2 ⭐⭐ 设计一个接口自动化测试平台

**参考对话：**

> **澄清**：用户是测试和开发；目标降低自动化门槛、统一执行和报告；日执行 10 万条用例。
>
> **架构**：
> 展现层（用例编排/任务/报告）→ 业务层（用例、环境、任务、报告服务）→ 调度层（MQ + XXL-Job/Celery）→ 执行层（执行引擎 + Executor 集群/K8s Job）→ 数据层（MySQL + Redis + OSS + ES）。
>
> **核心设计**：
> ① 用例三种模式：表单化（功能测试用）、YAML DSL（Git 管理）、代码模式（灵活），覆盖不同人群；
> ② 执行引擎：解析 DSL → 上下文变量池 → 步骤执行（HTTP/RPC/DB）→ 提取变量 → 断言 → 汇总；
> ③ 断言引擎：状态码、JSONPath、JSON Schema、DB、脚本断言；
> ④ 环境管理：环境配置独立，变量注入，禁止硬编码；
> ⑤ 报告：请求响应详情、断言差异、趋势大盘，通知到责任人。
>
> **难点**：
> ① 执行隔离：每次任务独立容器或按项目隔离 Agent 池；
> ② 用例依赖：优先独立，跨用例依赖用场景编排（DAG）显式声明；
> ③ 数据污染：数据工厂 + 清理任务；
> ④ 大规模报告：异步生成 + 对象存储 + ES 检索；
> ⑤ 幂等：任务去重键（用例集 + 环境 + 版本）。
>
> **选型理由**：Java 团队用 Spring Boot + XXL-Job；Python 团队用 FastAPI + Celery。执行器用 K8s Job 保证隔离与弹性。

**追问：**

🔁 怎么支持 gRPC/Dubbo？→ 协议适配层插件化，统一抽象 Request/Response；Dubbo 用泛化调用。
🔁 用例依赖太多怎么办？→ 分析依赖图，能独立尽量独立；必须依赖的走编排并明确前置检查；禁止隐式顺序依赖。
🔁 生产环境能跑吗？→ 默认禁止；只读巡检类任务需白名单 + 限流 + 审批。

## Q3 ⭐ 设计一个 Mock 平台

**参考对话：**

> **需求**：前后端联调、第三方依赖隔离、异常场景构造。
>
> **架构**：客户端（浏览器/App/CI）→ 代理层（mitmproxy/本地 Agent + CA 证书）→ 规则引擎（匹配 + 优先级）→ 响应层（静态/模板/脚本/转发真实服务）→ 管理端（规则 CRUD、命中日志、场景切换）。
>
> **匹配规则**：路径、方法、query、header、body 关键字的组合；精确匹配优先；冲突检测与命中日志。
>
> **响应能力**：状态码、延迟、超时、断连、多响应轮询、动态模板（Mock.js/JS）。
>
> **生效范围**：按环境、用户、App 版本、时间窗口。
>
> **难点**：
> ① HTTPS 解密：CA 证书 + 代理引导（移动端证书安装引导）；
> ② 性能：本地 Agent 代理减少中心压力；
> ③ 安全：脚本沙箱、规则权限隔离、禁止生产滥用。
>
> **演进**：与接口文档平台联动自动生成默认 Mock；命中数据沉淀为回归用例。

## Q4 设计一个造数平台

**参考对话：**

> **架构**：模板配置（字段规则 + 变量）→ 执行引擎（DAG 编排）→ 执行器（SQL/HTTP/MQ/脚本）→ 数据池（分配/回收/销毁）→ 对外 API（自动化框架调用）。
>
> **示例**：创建"用户 → 订单 → 支付"链路数据：SQL 建用户 → HTTP 创建订单 → MQ 推送支付消息，输出变量供后续引用。
>
> **难点**：
> ① 一致性：按外键依赖顺序执行，失败补偿；
> ② 幂等：唯一标识 + 存在即复用；
> ③ 回收：引用计数 + TTL + 手动清理；
> ④ 大批量：批量插入 + 异步任务 + 限速；
> ⑤ 安全：禁止生产写、SQL 白名单审计。

🔁 追问：怎么保证造的数据和真实业务一致？→ 优先走业务 API 造数（真实逻辑），SQL 仅用于性能数据和应急；数据模板由业务方评审。

## Q5 ⭐ 设计一个流量回放平台

**参考对话：**

> **架构**：采集（Agent 字节码增强/抓包，无侵入）→ 存储（MQ 削峰 + HBase/ES）→ 处理（清洗/去重/采样/脱敏/标签）→ 回放（调度 + 引擎 + 限流）→ 对比（字段级 Diff + 忽略规则 + 容差）→ 应用（回归/Bug 验证/压测造流量）。
>
> **核心机制**：
> ① 写流量：开关关闭 / Mock 下游 / 影子库，绝不污染生产；
> ② 时间敏感：时间 Mock，回放时替换 System.currentTimeMillis；
> ③ Diff 治理：忽略 traceId/时间戳、字段级容差、核心字段策略；
> ④ 覆盖率：回放时采集 JaCoCo，证明测试充分性；
> ⑤ 限流：控制回放速率，避免压垮目标环境。
>
> **难点**：流量去重与场景筛选、多下游 Mock 一致性、回放结果归因。

🔁 追问：和接口自动化的关系？→ 互补：自动化覆盖已知场景，流量回放覆盖真实长尾；回放发现的问题沉淀为新用例。

## Q6 设计一个精准测试平台

**参考对话：**

> **链路**：Git Diff → AST 解析生成方法调用链 → 变更方法推导变更/影响接口 → 用例知识库召回（倒排索引）→ 排序去重 → 推荐回归集 → 执行 + 覆盖率采集 → 度量。
>
> **核心指标**：精准率（推荐/实际变更）、漏测率、回归用例数下降、耗时下降。
>
> **技术**：javaparser/tree-sitter 做 AST；JaCoCo/jvm-sandbox 做覆盖率与运行时跟踪；Trace 补充动态调用链。
>
> **难点**：跨服务调用链、动态反射/SPI 的静态分析盲区、用例与代码映射的持续维护。
>
> **定位**：分层策略，不替代全量回归；核心链路永远保障。

## Q7 设计一个质量度量大盘

**参考对话：**

> **数据源**：Jira/TAPD（缺陷）、自动化平台（执行）、SonarQube（代码质量）、CI/CD（发布）、监控系统（线上）。
>
> **建模**：事实表（明细）+ 维度（项目/团队/时间/服务）+ 定时聚合汇总表 → 可视化。
>
> **指标**：逃逸率、提测打回率、覆盖率、回归耗时、门禁通过率、P0 故障、MTTR。
>
> **难点**：口径统一（先定义再开发）、实时性与性能平衡、防止指标游戏、指标要能下钻归因。
>
> **原则**：每个指标对应一个改进行动，否则就是噪音。

## Q8 设计一条 CI 流水线（含测试）

**参考对话：**

> **阶段**：Lint/静态扫描 → 单测 + 覆盖率 → 构建 → 部署测试环境 → 接口/契约/冒烟 → 核心 UI → 质量门禁 → 预发 → 灰度。
>
> **分层触发**：push 跑快检查；MR 加小回归；合并跑核心回归；夜间全量；发版前全链路。
>
> **优化**：缓存依赖、并行分片、精准测试、增量覆盖。
>
> **失败处理**：JUnit/Allure 归档、失败截图/Trace、通知到人、Flaky 隔离。
>
> **门禁**：静态 0 blocker、增量覆盖 80%、P0 用例全过、安全无高危。

## Q9 设计一套测试环境方案（200 人团队）

**参考对话：**

> **分层**：本地 → dev → test（共享主环境）→ 预发（近生产）→ 生产。
>
> **痛点与方案**：
> ① 环境抢占 → 按需动态环境：MR 触发 Helm 拉起独立 Namespace，跑完销毁；
> ② 版本不一致 → 镜像化 + IaC（Helm）；
> ③ 配置漂移 → 配置中心版本化 + 审计；
> ④ 依赖不稳 → 统一 Mock 平台；
> ⑤ 数据污染 → 数据隔离 + 唯一前缀 + 定时重置；
> ⑥ 环境不可知 → 健康检查 + 状态页 + 告警。
>
> **成本控制**：共享基础中间件 + 按需拉起应用实例；TTL 自动回收。

## Q10 开放追问合集

| 追问 | 参考回答 |
| --- | --- |
| 平台建设怎么立项？ | 找高频痛点 → 量化成本 → 小范围 MVP → 用数据争取资源 |
| 平台怎么推广？ | 先解决一个团队痛点，做样板；培训 + 文档 + 结对；把人从重复劳动中解放 |
| 平台怎么衡量价值？ | 接入团队数、日活、执行量、节省人日、缺陷拦截数 |
| 自研还是开源？ | 核心能力自研（贴合业务），通用能力用开源（报告/调度）；避免重复造轮子 |
| 数据量大怎么办？ | 归档冷数据、分表、预聚合、ES 检索、对象存储 |
| 怎么保证平台稳定？ | 限流、熔断、降级、灰度发布、自身监控（Prometheus + 告警） |
| 权限怎么做？ | RBAC + 项目隔离 + 操作审计；生产操作二次确认 |
| 未来的演进方向？ | 与精准测试/AI 结合：智能推荐用例、自动生成、失败归因 |
