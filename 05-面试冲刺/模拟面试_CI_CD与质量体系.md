## 第一轮：CI/CD 与工程化

### Q1 ⭐ CI/CD 是什么？测试在流水线中的位置？

**参考话术：**

> CI 是频繁合并代码并自动构建验证；CD 是持续交付（随时可发布）和持续部署（自动发布）。
> 测试贯穿整条流水线：提交阶段跑 Lint/单测/静态扫描 → 构建 → 部署测试环境 → 接口/契约/冒烟 → UI 核心链路 → 发布预发 → 灰度 → 生产验证。
> 快检查前置（分钟级反馈），慢用例后置（夜间全量），这是流水线设计的基本原则。

🔁 追问：怎么让流水线又快又稳？→ 分层触发 + 缓存依赖 + 并行分片 + 精准测试（只跑变更影响）+ Flaky 隔离。

---

### Q2 ⭐ 你们的质量门禁有哪些？

| 门禁 | 工具 | 阈值 |
| --- | --- | --- |
| 静态扫描 | SonarQube | 0 Blocker、无新增严重问题 |
| 单测 | JUnit/pytest | 通过率 100% |
| 覆盖率 | JaCoCo/coverage | 增量 ≥ 80% |
| 接口回归 | 自研框架 | P0 全过 |
| 安全扫描 | SCA/SAST | 无高危 |
| 构建时长 | CI | 不劣化 |

门禁落地节奏：先"只报告不阻断" → 核心服务先卡 → 遇到误报有豁免流程（审批+记录+期限）。

🔁 追问：为什么用增量覆盖率？→ 存量低时全量永远不达标，只卡新代码公平且可落地。

---

### Q3 ⭐ 覆盖率怎么统计？服务端接口覆盖率怎么采？

**答：**

> 单元测试覆盖率：JaCoCo（Java）/coverage.py（Python）/istanbul（前端）。
> 服务端接口测试覆盖率：给服务挂 JaCoCo Agent（`-javaagent:jacocoagent.jar`），运行接口用例时采集；结束后 dump 覆盖率报告；增量覆盖率=变更行覆盖数/变更行总数。
> 注意覆盖率≠有效性，要结合缺陷拦截率和变异测试看质量。

### Q4 Jenkins 和 GitLab CI 怎么选？

**答：** Jenkins 插件多（1800+）、定制强，但自运维成本高；GitLab CI 与代码库一体、YAML 简单、K8s Runner 原生，适合已用 GitLab 的团队。核心还是流水线设计能力，工具其次。

### Q5 Jenkins Pipeline 怎么写？（说出结构即可）

**答：** 声明式 pipeline：agent（执行节点）→ stages（Checkout/Build/UnitTest/APITest/QualityGate/Deploy）→ post（always/failure 通知与报告归档）。要点：凭据用 Credentials 管理、构建环境用 Docker Agent、报告用 JUnit/Allure 归档、门禁用 SonarQube waitForQualityGate。

### Q6 测试环境怎么治理？

**参考话术：**

> 六大问题：随意重启、版本不一致、配置漂移、依赖不稳、数据互相覆盖、不可用无感知。
> 手段：镜像化/IaC 部署保证一致；配置中心版本化 + 审计；依赖统一 Mock；数据隔离 + 唯一前缀 + 定时重置；环境健康检查 + 状态页 + 责任人。
> 云原生方案：每个 MR 用 Helm 拉起独立 Namespace，跑完销毁，彻底解决抢占。

### Q7 Docker 对测试的价值是什么？

**答：** 环境一致性（开发/测试/CI 同镜像）、秒级启动依赖（MySQL/Redis/Mock）、隔离性（每人独立环境）、可复现（版本固定）。测试镜像要固定依赖版本、配置时区、非 root、健康检查。

### Q8 K8s 里怎么跑自动化测试？

**答：** 用 Job/CronJob 跑测试容器；用例并行用 Pod 分片；Namespace 隔离环境；ConfigMap/Secret 注入配置；结果写入对象存储或 PVC；Jenkins/GitLab Runner 都可动态创建 Pod，用完即毁。

### Q9 UI 自动化在 CI 里跑不动/不稳定，怎么优化？

**答：** ① 镜像固化浏览器版本；② 无头模式 + 合理等待；③ 用例分片并行；④ Mock 不稳定依赖；⑤ 失败上传 Trace/视频/截图；⑥ Flaky 隔离区不阻塞门禁；⑦ 夜间跑全量，MR 只跑核心。

### Q10 发布策略有哪些？测试怎么配合？

| 策略 | 测试配合 |
| --- | --- |
| 蓝绿 | 切流前完成绿环境回归 |
| 灰度/金丝雀 | 灰度指标监控 + 自动冒烟 |
| 滚动 | 观察实例健康与成功率 |
| 回滚 | 回滚演练 + 数据兼容验证 |

发布检查单：冒烟过、脚本可回滚、开关就绪、监控配置、回滚预案。

## 第二轮：测试左移右移与度量

### Q11 ⭐ 你怎么理解测试左移？落地过什么？

**参考话术：**

> 左移不是"测试提前介入"这么简单，而是质量责任前移：需求阶段定义可测的验收标准，设计阶段做可测性评审，编码阶段把单测、契约测试、静态扫描接入 CI 门禁。
> 我推动过的落地：增量覆盖率门禁（新代码 80%）+ 提测标准（冒烟不通过直接打回）+ 契约测试解决联调等待。结果提测打回率从 20% 降到 8%，联调问题减少一半。

🔁 追问：怎么推动开发写单测？→ 数据说话（覆盖率与线上缺陷相关性）+ 增量门禁 + 提供脚手架 + 质量大盘公示，而不是单纯下指标。

### Q12 ⭐ 测试右移是什么？怎么做？

**答：** 发布后持续保障：灰度验证、监控告警（业务指标优先）、合成拨测、线上数据巡检/对账、A/B 实验、用户反馈闭环。目标是在用户之前发现问题，并能在分钟级止损。

### Q13 ⭐ 质量度量指标有哪些？

| 类型 | 指标 |
| --- | --- |
| 过程 | 执行率、缺陷密度、提测打回率、门禁通过率 |
| 结果 | 缺陷逃逸率、P0 故障数、可用率、MTTR |
| 趋势 | 自动化覆盖率、回归耗时、Flaky 率 |

🔁 追问：逃逸率怎么算？→ 线上缺陷 /（线上 + 测试阶段缺陷），衡量测试有效性，越低越好。

🔁 追问：为什么不用 Bug 数考核测试？→ 会诱导拆 Bug、拒收问题；指标要能归因到行动，否则就是数字游戏。

### Q14 DORA 四指标是什么？

**答：** 部署频率、变更前置时间、变更失败率、故障恢复时间。精英团队：按需部署、前置 <1 小时、失败率 0–15%、恢复 <1 小时。

### Q15 如何评估测试是否充分？

**答：** 需求覆盖（用例-需求双向追溯）、增量代码覆盖、风险覆盖（变更热点 × 历史缺陷 × 业务热度）、缺陷发现曲线收敛、上线后逃逸率。给一个组合答案，不要只说覆盖率。

## 第三轮：缺陷与线上质量

### Q16 ⭐ 开发不认可 Bug，怎么处理？

**参考话术：**

> ① 自查：环境/数据/需求理解；② 用证据：复现步骤、日志、Trace、录屏、请求响应；③ 回到验收标准（AC）而不是主观判断；④ 评估影响面（用户数、是否资损）；⑤ 上升到产品/技术负责人裁决；⑥ 事后沉淀规范，减少同类争议。

### Q17 ⭐ 线上偶发超时，你怎么排查？

**答：**

> ① 定界：影响面（用户/接口/时段）；② Trace 定位慢 Span：是 DB、下游还是自身；③ 日志按 traceId 捞取，看错误模式；④ 资源指标：GC、连接池、线程池、CPU；⑤ 偶发问题大概率是资源争抢、连接池配置、GC 停顿或下游抖动；⑥ 用压测/混沌注入放大复现；⑦ 修复后加监控和回归用例。

### Q18 线上出现 P0 故障，你的处理流程？

**答：** 止损优先（回滚/开关/扩容）→ 通报（影响面与处理进展）→ 定位根因 → 修复验证 → 复盘（时间线、根因、行动项、责任人）→ 补充监控与用例 → 演练验证。

### Q19 复盘怎么做才有效？

**答：** 对事不对人；时间线还原；5 Why 追到流程/规范层；行动项必须可落地、有负责人和期限；跟踪闭环；把教训转成监控、用例、检查单。避免"注意一下""加强意识"这种空行动项。

### Q20 缺陷生命周期是什么？

新建 → 分配 → 修复中 → 已修复 → 验证 → 关闭；拒绝/延期需复核并记录理由；持续跟踪遗留缺陷并在发布评估中明确风险。

## 第四轮：开放题（主管面高频）

### Q21 ⭐⭐ 你怎么保证测试质量？

**参考话术（全流程闭环）：**

```
需求：参与评审，输出可测性意见与验收标准
设计：制定测试策略，分层与风险优先级
编码：推动单测/契约/静态扫描，接 CI 门禁
测试：用例设计 + 自动化 + 专项 + 探索性测试
发布：冒烟、灰度、回滚预案、发布检查单
线上：监控告警、巡检、复盘、用例反哺
度量：逃逸率/覆盖率/稳定性大盘驱动改进
```

### Q22 测试时间被压缩一半，怎么办？

**答：** 按风险裁剪（保核心与变更影响面）→ 自动化跑回归 → 输出风险清单让项目组决策 → 灰度与开关兜底 → 上线后重点监控 → 事后补测和复盘。核心是**把测试问题翻译成业务风险**。

### Q23 如何从 0 推动一个质量改进项目？

**答：** 选痛点（用数据证明）→ 小范围试点（拿结果）→ 形成 SOP 与工具 → 度量收益并公示 → 争取管理层支持 → 推广复制 → 防止回退（门禁与流程固化）。

### Q24 测试如何体现价值？

**答：** 拦截缺陷（避免资损）、提效（自动化/平台量化人日）、预防（左移减少缺陷产生）、保障（发布信心与线上稳定）。每个方向都用数据说话。

### Q25 你未来的职业规划？

**参考话术：** "短期做深质量工程：把自动化、精准测试和 AI 辅助测试在业务里落地；中期往质量架构走，能设计质量体系和平台；长期希望成为既懂工程又懂业务的测试专家，带小团队。和贵司这个岗位的方向很契合。"
