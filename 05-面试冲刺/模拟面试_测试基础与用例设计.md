## 第一轮：开场与经历

### Q1 ⭐ 自我介绍

**参考答话术：**

> 我是 XX，X 年测试/测试开发经验，目前在 XX 负责 XX 业务的质量保障。主要做三件事：
> 第一，自动化体系：主导接口和 UI 自动化框架，覆盖核心场景 500+，回归从 8 小时缩到 40 分钟，冒烟稳定性 99%。
> 第二，效能工具：做了造数平台和 Mock 服务，服务 3 个团队，每月节省约 30 人日。
> 第三，质量体系：推动单测门禁和精准测试落地，线上缺陷逃逸率下降 40%。
> 技术上擅长 Python 工程化和 CI/CD 集成，最近在研究 Agent 评测和 AI 辅助测试。

**加分点：** 每句话都带量化；结构清晰（业务 + 三件事 + 技术栈）。
**踩雷：** 从大学经历开始讲、讲满 5 分钟、只说"踏实肯干"。

🔁 追问：你最有成就感的项目？→ 转 STAR（见 Q2）。

---

### Q2 ⭐ 介绍一个你最复杂的项目（STAR）

**参考答话术：**

> **背景**：大促前回归压力大，2000+ 用例全量回归要 8 小时，经常漏测。
> **任务**：我负责把核心回归压缩到 1 小时内，同时不降低缺陷拦截率。
> **行动**：
> ① 分层改造：把用例按业务链路分级，P0 场景 87 条必跑；
> ② 框架升级：接口用例数据驱动 + pytest-xdist 8 并发，单机 10 分钟跑完；
> ③ 精准推荐：接入代码 Diff + 调用链分析，按变更推荐回归集；
> ④ 稳定性治理：Flaky 用例进隔离区，冒烟稳定性从 92% 提到 99.5%。
> **结果**：回归 40 分钟，缺陷拦截率不降反升，版本周期缩短半天；方案复制到 3 个团队。

**加分点：** 行动分点、每点有技术细节、结果量化。
**踩雷：** 只说"我负责测试"，不说自己的决策和难点。

🔁 追问：最大的难点是什么？→ 选"Flaky 治理"或"数据隔离"，讲具体案例。

### Q3 为什么做测试/测开？和开发的区别？

**参考答话术：**

> 开发的产出是功能，测开的产出是"质量与效率"——用工程手段让问题更早暴露、让团队更敢发版。我喜欢这种"既懂技术又懂风险"的位置。差别在于视角：开发关注实现正确，测开关注失败模式、边界、成本和长期稳定性。

## 第二轮：测试流程与理论

### Q4 ⭐ 你们项目的测试流程是怎样的？

**参考答话术（按阶段）：**

> 需求评审（测试参与，提可测性和风险）→ 测试计划与策略（分层与优先级）→ 用例设计评审 → 开发自测与提测标准（冒烟必须先过）→ 执行（功能 + 接口自动化 + 专项）→ 缺陷管理与回归 → 测试报告与上线评估 → 灰度/上线验证 → 线上监控与复盘。

🔁 追问：哪个阶段最能体现测试价值？→ 需求阶段（缺陷预防成本最低）+ 上线阶段（逃逸控制）。

🔁 追问：敏捷下流程怎么变？→ 迭代内：需求澄清会 → 用例与自动化并行 → CI 每日回归 → 迭代末验收；强调"持续测试"而非阶段门。

---

### Q5 ⭐ 如果给你一个从来没有测试过的系统，你怎么开展测试？

**参考话术（万能框架）：**

```
1. 摸底：业务目标、用户角色、核心链路、架构与依赖、历史事故
2. 定策略：风险排序（资损/高频/新变更），确定分层与专项
3. 建环境与数据：环境可用性、基础数据、Mock 依赖
4. 快速冒烟：先跑通主流程，建立信心和基线
5. 系统测试：功能 → 接口 → 异常 → 边界 → 权限 → 并发
6. 专项：性能、安全、兼容、稳定性按风险选择
7. 沉淀：用例库、自动化、监控、发布检查单
```

---

### Q6 测试计划包含哪些内容？

**答：** 范围（做/不做）、目标与出口标准、策略与分层、资源与排期、环境与数据、风险与应对、交付物（用例/报告）、沟通与里程碑。背这 8 项即可。

---

### Q7 软件达到什么标准可以上线？

**答：**

- 门禁全绿：单测、静态扫描、增量覆盖率达标；
- P0/P1 用例全部通过，冒烟通过；
- 遗留缺陷有明确结论（修复/延期/接受风险）；
- 专项达标（性能、安全按需）；
- 发布检查单完成：脚本、开关、监控、回滚方案；
- 灰度指标正常，回滚可在分钟内完成。

---

### Q8 测试左移/右移你怎么理解？做过哪些？

**答：**

> 左移是把质量活动前置：需求阶段确认验收标准 AC，设计阶段做可测性评审，编码阶段推动单测和契约测试进 CI；我做过的是把增量覆盖率和 SonarQube 接入门禁，提测打回率从 20% 降到 8%。
> 右移是发布后继续保障：灰度、监控告警、线上巡检、用户反馈闭环；我搭过核心链路拨测和订单量对账巡检。

🔁 追问：左移最大的阻力？→ 开发和测试的目标不一致，要用数据和质量大盘说话，先"只报告不阻断"。

## 第三轮：用例设计方法

### Q9 ⭐ 用例设计方法有哪些？分别什么场景用？

| 方法 | 适用场景 |
| --- | --- |
| 等价类划分 | 输入域大，无需穷举（账号、金额） |
| 边界值 | 有数值/长度边界（分页、限额） |
| 判定表/因果图 | 多条件组合与业务规则（优惠券叠加） |
| 正交实验 | 多参数组合爆炸（配置项） |
| 场景法 | 业务流程（下单→支付→发货） |
| 状态迁移 | 状态机系统（订单、工单） |
| 错误推断 | 经验补充（历史缺陷、并发、网络） |

**回答技巧：** 说完方法立刻接一句"实际是组合使用，比如优惠券用判定表 + 边界值"。

---

### Q10 等价类和边界值的关系？边界值取哪些点？

**答：** 等价类划分"测哪些"，边界值测"最容易出错的地方"，两者互补。边界取上点（边界本身）、内点（边界内）、离点（边界外最近点）：如范围 [1,100]，取 0、1、2、50、99、100、101。

🔁 追问：为什么边界容易出错？→ 循环条件、比较符号（< vs <=）、数组下标、金额精度等实现细节。

---

### Q11 状态迁移法怎么用？举个例子。

**答：** 订单状态：待支付 → 已支付 → 已发货 → 已完成；覆盖：合法迁移全路径 + 非法迁移（已完成订单不能取消）+ 触发条件（超时未支付自动取消）+ 并发迁移（支付的同时取消）。

## 第四轮：场景设计题（现场出题，重点）

> 通用答题结构：**功能（正常/异常/边界）→ 数据（状态/一致性）→ 权限与安全 → 性能与并发 → 兼容与体验**。先给框架再展开，不要一上来就堆点。

### Q12 ⭐ 设计"登录"功能的测试用例

**参考框架：**

| 维度 | 用例 |
| --- | --- |
| 正常 | 正确账号密码、手机号/邮箱/用户名多种方式、记住我 |
| 异常 | 密码错误、账号不存在、空值、格式错误、超长、特殊字符 |
| 边界 | 密码最小/最大长度、错误次数上限（第 N 次锁定） |
| 安全 | 撞库限流、验证码绕过、SQL 注入、密码明文传输、Token 过期/伪造、越权 |
| 会话 | 多端登录、互踢、退出后 Token 失效、并发登录 |
| 体验 | 加载态、错误提示不泄露账号是否存在、回车提交 |
| 兼容 | Web/App/小程序、浏览器、暗黑模式 |

🔁 追问：错误提示"账号不存在"和"密码错误"要不要区分？→ 安全上不区分（防枚举），体验上可通过其他方式（验证码）平衡。

### Q13 ⭐ 设计"购物车"的测试用例

- 加购：商品下架/售罄/限购、数量边界（0、-1、最大）、多规格、重复加购合并；
- 价格：促销价、会员价、优惠券预计算、价格变动提示；
- 结算：全选/单选、失效商品处理、库存扣减时机（下单 vs 支付）；
- 数据：多端同步、登录前后合并、刷新持久化；
- 权限：他人购物车不可见；
- 性能：大购物车（500 件）、并发修改同一购物车；
- 异常：网络失败回滚、重复提交。

### Q14 ⭐ 设计"支付"的测试用例

- 渠道：微信/支付宝/银行卡/余额、单笔/组合支付；
- 金额：0.01、精度、优惠后金额、超限、多币种；
- 状态：支付成功/失败/超时/取消、回调丢失重试、重复回调幂等；
- 一致性：订单状态与流水对账、退款全流程、部分退款；
- 并发：同一订单并发支付、余额并发扣减；
- 安全：金额篡改、越权替他人支付、重放攻击、敏感信息脱敏；
- 异常：支付中杀进程、断网恢复、渠道维护；
- 性能：峰值 TPS、回调洪峰。

### Q15 ⭐ 设计"微信红包"的测试用例

| 维度 | 关注点 |
| --- | --- |
| 金额 | 总额=各红包之和（精度）、单个区间、剩余金额校验 |
| 并发 | 100 人同时抢、一人只能抢一次、抢完提示 |
| 状态 | 24h 未领取退回、重复领取、已领取再点开 |
| 权限 | 非群成员不可抢、指定红包不可转发 |
| 数据 | 余额与流水一致、并发入账不重复 |
| 异常 | 领取中杀进程、网络重试、服务降级 |
| 安全 | 篡改金额、脚本刷红包、风控拦截 |
| 性能 | 春节峰值、热点群、冷热分离 |

### Q16 设计"搜索"功能的测试用例

- 输入：空、空格、超长、特殊字符、emoji、拼音、错别字、大小写；
- 结果：相关度、排序规则、分页、无结果提示、高亮；
- 过滤：类目、价格区间、排序切换、组合筛选；
- 性能：热门词 QPS、深分页、超时降级；
- 安全：XSS、SQL 注入、敏感词、诱导词；
- 体验：搜索建议、历史记录、纠错、A/B 相关性。

### Q17 设计"文件上传"的测试用例

- 格式白名单、大小上限、空文件、改名（双扩展名）、超大文件；
- 断点续传、秒传（MD5）、并发上传、重复上传；
- 恶意文件（木马、SVG XSS）、压缩炸弹、路径穿越文件名；
- 存储：临时文件清理、CDN 刷新、权限（他人文件不可下载）；
- 弱网：超时重试、进度准确、失败恢复。

### Q18 一个输入框怎么测？

**速答：** 功能（正常输入/提交/清空）；输入域（空、空格、超长、特殊字符、emoji、数字/字母/中文、粘贴、全角半角）；交互（回车、Tab、联想、禁用态）；安全（注入、XSS、敏感词）；体验（占位符、错误提示、自动聚焦）；兼容（输入法、移动键盘类型）。

## 第五轮：缺陷管理与沟通

### Q19 ⭐ 开发说"这不是 Bug"，你怎么办？

**参考话术：**

> 我会先自查三类情况：是不是环境/数据问题、是不是需求理解不一致、是不是我的预期没有依据。确认是问题后：
> ① 用证据说话：复现步骤、日志、Trace、录屏、接口请求响应；
> ② 回到需求与验收标准（AC），而不是"我觉得"；
> ③ 给影响面评估：影响多少用户/是否资损；
> ④ 仍有分歧就升级到产品/技术负责人裁决；
> ⑤ 事后把这类争议沉淀成规范或检查清单，减少下次扯皮。

### Q20 🔁 线上出现 Bug，你的处理流程？

**答：** ① 快速定界（影响面）；② 止损优先（回滚/开关/降级）；③ 定位根因（Trace/日志/变更比对）；④ 修复并验证（含回归防护）；⑤ 复盘 5 Why + 行动项；⑥ 用例反哺。

### Q21 Bug 怎么定级？

P0 致命（主流程不可用/资损/数据丢失）、P1 严重（核心功能异常无绕行）、P2 一般（有绕行）、P3 轻微（体验/文案）。补充一句："定级还会参考发生频率和影响用户比例。"

## 第六轮：策略与开放题

### Q22 ⭐ 你怎么保证测试质量？

```
策略：风险驱动，明确出口标准
分层：单测（开发）+ 接口（主力）+ UI（核心链路）
工程：自动化 + CI 门禁 + 环境数据治理
专项：性能、安全、兼容按风险选
发布：冒烟 + 灰度 + 回滚预案 + 监控
闭环：逃逸率复盘 + 用例反哺 + 度量大盘
```

### Q23 测试时间不够怎么办？

**答：** 风险裁剪保 P0 → 自动化跑核心回归 → 明确风险清单让项目组决策"带风险上线" → 灰度与回滚兜底 → 事后补测与复盘。关键是把"测试没测完"翻译成"业务风险清单"。

### Q24 怎么衡量测试的价值/有效性？

- 缺陷拦截：测试阶段拦截率、逃逸率；
- 效率：自动化覆盖率、回归耗时下降、平台节省人日；
- 预防：提测打回率下降、需求阶段发现问题数；
- 业务：线上故障数、可用率、故障恢复时长。

### Q25 你觉得你最大的缺点是什么？

**参考话术：** "我以前过度追求技术方案完美，比如造数平台第一版做得很重，交付慢。现在我会先对齐业务目标，用最小可用版本验证价值再迭代。"——真实 + 有改进行动。
