# 🏛️ 后端服务常见架构与测试策略（完整版）

> 从单体到微服务、事件驱动、Service Mesh、Serverless 的演进全景；
> 每种架构"是什么、优缺点、适用场景"，以及**测试视角要重点验证什么**。

---

## 一、架构演进主线

```
单体 → 分层 → SOA → 微服务 → 云原生（容器/Service Mesh）
                              ├→ 事件驱动 / CQRS
                              ├→ Serverless / FaaS
                              └→ 分布式 / 多活
```

驱动演进的三股力量：**业务复杂度增长、团队规模扩大、交付频率提升**。

---

## 二、单体架构（Monolithic）

**特点：**

- 所有模块在同一进程，一次构建部署；
- 开发简单、调试方便、事务天然一致。

**问题：** 代码耦合、发布牵一发动全身、扩展只能整体扩容、技术栈锁定。

**适用：** 初创项目、业务简单、小团队（< 10 人）。

**示例：** 一个 Spring Boot 应用包含用户、商品、订单、支付模块。

**测试重点：**

- 模块间调用与事务边界；
- 回归范围大（任何改动都可能影响全局）；
- 发布前的全量冒烟与核心链路回归；
- 数据库变更的兼容性。

---

## 三、分层架构（Layered）

**特点：** 表示层（Controller）→ 业务层（Service）→ 数据层（DAO）→ DB，职责清晰。

**适用：** 企业后台、传统业务系统。

**测试重点：**

- 分层职责是否被破坏（Controller 写业务逻辑）；
- SQL 集中在 DAO 层便于治理；
- 异常在层间的传递与转换。

---

## 四、SOA（面向服务架构）

**特点：** 服务拆分 + ESB/RPC 连接，强调复用；ESB 易成瓶颈与单点。

**适用：** 银行、政务等大型传统企业。

**测试重点：**

- 服务契约（WSDL/接口文档）一致性；
- ESB 路由与协议转换正确性；
- 服务复用带来的"改一处影响多方"回归。

---

## 五、微服务架构

**特点：** 按业务域拆分为独立服务，独立部署/扩缩容，HTTP/gRPC/MQ 通信，容器化。

**配套能力（缺一不可）：**

| 能力 | 组件示例 | 测试关注 |
| --- | --- | --- |
| 服务注册发现 | Nacos、Consul、Eureka | 摘除/上线期间的流量无损 |
| 配置中心 | Nacos、Apollo | 多环境隔离、动态生效、回滚 |
| 网关 | Spring Cloud Gateway、Kong | 路由、鉴权、限流 |
| 链路追踪 | SkyWalking、Jaeger | traceId 贯通 |
| 服务治理 | 限流、熔断、降级 | 阈值触发与恢复 |
| 可观测性 | Metrics/Logging/Tracing | 问题可定位 |

**优点：** 独立部署、弹性伸缩、故障隔离、技术异构。
**缺点：** 分布式复杂度、数据一致性、联调与测试成本高。

**测试重点：**

- **契约测试**防止接口漂移；
- 服务依赖 Mock 与联调策略；
- 分布式事务与最终一致性（对账）；
- 超时/重试/熔断/降级组合行为；
- 服务实例故障时的负载均衡与自愈；
- 多服务版本共存的兼容性（灰度）。

---

## 六、API 网关与 BFF

| 模式 | 作用 |
| --- | --- |
| API 网关 | 统一入口：路由、鉴权、限流、灰度、日志 |
| BFF（Backend for Frontend） | 面向端（App/Web/小程序）裁剪聚合接口 |

**测试重点：**

- 路由规则（含灰度/AB 路由）；
- 鉴权在网关与服务内的双重校验；
- 限流阈值与拒绝策略；
- BFF 聚合接口的降级（某个下游挂了的兜底）；
- 端侧数据裁剪正确性（不多给不少给）。

---

## 七、Service Mesh（服务网格）

**特点：** 把流量治理（重试、熔断、mTLS、观测）下沉到 Sidecar（Envoy），业务无侵入。

**适用：** 大规模微服务、多语言异构、需要统一治理。

**测试重点：**

- Sidecar 注入后的连通性与性能损耗；
- 流量规则（路由/镜像/故障注入）生效范围；
- mTLS 证书轮换不影响业务；
- 与 K8s 探针/滚动发布的配合。

---

## 八、事件驱动架构（EDA）

**特点：** 以事件/消息为核心，生产者 → Broker → 消费者解耦，天然削峰填谷。

**关键问题：**

| 问题 | 方案 | 测试 |
| --- | --- | --- |
| 消息丢失 | 确认 + 持久化 + 手动 ACK | 故障注入验证不丢 |
| 消息重复 | 幂等消费 | 重投验证 |
| 顺序 | 同 key 同分区 | 并发发送验证顺序 |
| 积压 | 监控 + 扩容消费 | 压测消费速率 |
| 死信 | 死信队列 + 告警 | 异常消息处理 |

**测试重点：** 端到端最终一致性、消费者幂等、消息 schema 演进兼容、延迟与积压。

---

## 九、CQRS 与事件溯源（Event Sourcing）

- **CQRS**：读写模型分离，写模型负责一致性，读模型为查询优化；
- **事件溯源**：状态由事件序列重放得出，天然审计。

**测试重点：**

- 读写模型数据同步延迟与最终一致；
- 事件重放的幂等与顺序；
- 读模型的补偿重建；
- 事件 schema 版本兼容。

---

## 十、数据架构

| 模式 | 说明 | 测试重点 |
| --- | --- | --- |
| 读写分离 | 主写从读 | 主从延迟导致"写后读不到" |
| 分库分表 | 水平拆分 | 跨分片查询、路由正确性、扩容迁移 |
| 缓存 | Redis 多级缓存 | 一致性、穿透/击穿/雪崩 |
| 冷热分离 | 热数据缓存/冷数据归档 | 归档后查询可用 |
| 数据同步 | CDC/binlog | 目标端一致性、断点续传、乱序 |

## 十一、高可用设计

| 手段 | 说明 | 测试验证 |
| --- | --- | --- |
| 负载均衡 | Nginx/LVS/K8s Service | 实例摘除/恢复无损 |
| 限流 | 令牌桶/漏桶 | 阈值、拒绝策略 |
| 熔断 | 失败率触发 | 触发、半开、恢复 |
| 降级 | 兜底数据/关非核心 | 开关生效、可回滚 |
| 隔离 | 线程池/集群隔离 | 一个依赖挂不扩散 |
| 多活/容灾 | 同城双活、异地多活 | 切流演练、数据一致性 |

---

## 十二、Serverless / FaaS

**特点：** 函数级部署，按需伸缩计费，事件驱动。

**问题：** 冷启动延迟、状态管理、调试与本地复现困难。

**测试重点：** 冷启动性能、并发限制与扩容、事件源集成正确性、超时与重试语义（至少一次）、成本监控。

---

## 十三、架构对比表

| 架构类型 | 特点 | 优点 | 缺点 | 典型场景 | 举例 |
| --- | --- | --- | --- | --- | --- |
| 单体 Monolithic | 所有模块一个应用 | 开发部署简单 | 耦合、难扩展 | 小型系统 | 一个 Spring Boot 应用 |
| 分层 Layered | Controller/Service/DAO | 职责清晰 | 复杂业务灵活差 | 企业后台 | Java EE 三层 |
| SOA | 服务 + ESB/RPC | 复用 | ESB 瓶颈 | 银行/政务 | 早期 Dubbo |
| 微服务 | 独立部署的服务群 | 弹性、隔离 | 治理复杂 | 大型互联网 | 商品/订单/支付服务 |
| API 网关/BFF | 统一入口与端侧裁剪 | 安全、聚合 | 网关单点风险 | 多端产品 | Spring Cloud Gateway |
| Service Mesh | Sidecar 治理 | 无侵入、多语言 | 性能损耗、复杂度 | 大规模微服务 | Istio + Envoy |
| 事件驱动 EDA | 消息解耦 | 异步、削峰 | 调试难、一致性 | 高并发异步 | Kafka 订单事件 |
| CQRS/ES | 读写分离、事件溯源 | 查询优化、可审计 | 复杂度高 | 金融、审批 | 账户流水 |
| Serverless | 函数级运行 | 按需计费、免运维 | 冷启动、状态 | 事件任务 | AWS Lambda |
| 分布式 | 多机数据分布 | 高可用、扩展 | CAP 权衡 | 大规模系统 | Redis Cluster、分库分表 |

## 十四、架构选型决策框架

```
业务复杂度 × 团队规模 × 交付频率 × 运维能力 = 架构演进时机
```

| 信号 | 建议 |
| --- | --- |
| 团队 < 10 人、业务单一 | 单体 + 分层，别急着微服务 |
| 多团队并行、发布互相阻塞 | 按业务域拆服务 |
| 多端产品、接口聚合需求 | 引入 BFF |
| 跨语言、治理规则统一诉求强 | Service Mesh |
| 强异步/削峰场景 | 事件驱动 + MQ |
| 高并发读、读写特性差异大 | CQRS + 缓存 |
| 波动大、事件式任务 | Serverless |

**反模式：** 为技术而架构、微服务拆得过细（分布式单体）、没有配套治理就上微服务。

## 十五、演进实例：电商架构

```
阶段1 单体：一个应用 + 一个库（日订单 1 万）
阶段2 分层+读写分离：热点读走缓存（日订单 10 万）
阶段3 微服务：用户/商品/订单/支付/库存独立（日订单百万）
阶段4 事件驱动：下单事件 → 异步扣库存、发券、通知（削峰）
阶段5 多活+单元化：同城双活、异地容灾（大促峰值）
```

**每个阶段的测试策略变化：**

| 阶段 | 测试重心 |
| --- | --- |
| 单体 | 全量回归、事务一致性 |
| 读写分离 | 主从延迟、写后读 |
| 微服务 | 契约、Mock、分布式事务、故障隔离 |
| 事件驱动 | 幂等、顺序、积压、最终一致 |
| 多活 | 切流演练、跨单元数据一致、容灾 |

## 十六、面试问答

**Q1：单体、SOA、微服务的区别？**
> 单体是一个进程内模块化；SOA 通过 ESB/RPC 复用企业服务，中心化；微服务按业务域独立部署，去中心化治理，强调自治与容错。核心差异是**耦合边界与部署单元的粒度**。

**Q2：微服务下测试最大的挑战是什么？**
> 服务边界与联调成本：契约漂移、依赖不可控、数据一致性、故障组合爆炸。解法：契约测试、Mock/服务虚拟化、流量回放、分布式链路追踪、混沌工程。

**Q3：为什么需要 API 网关？**
> 统一入口解决横切关注点：鉴权、限流、路由、灰度、日志；避免每个服务重复实现。测试要重点验路由、鉴权、限流与降级。

**Q4：事件驱动架构怎么保证消息不丢不重不乱序？**
> 不丢：生产确认 + 持久化 + 消费手动 ACK；不重：消费幂等（唯一键/去重表）；不乱序：同 key 同分区 + 顺序消费。测试用故障注入与重投验证。

**Q5：怎么选择要不要上微服务？**
> 看组织与交付痛点：多团队发布互相阻塞、模块扩展需求差异大时才拆；团队小、业务单一时单体更快。架构是组织与业务的映射，不是越新越好。

---

## 十七、总结

> 架构没有银弹，只有**匹配**：业务复杂度、团队规模、交付频率、运维能力。
> 测试的价值在于：**无论架构怎么演进，都能准确识别出该架构下的质量风险点**，并用契约、Mock、回放、混沌等手段系统化验证。
