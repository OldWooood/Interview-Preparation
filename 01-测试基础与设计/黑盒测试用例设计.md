# 📦 黑盒测试用例设计完全指南

> 从需求出发，系统化选择测试设计方法：等价类 → 边界值 → 判定表 → 因果图 → 正交/成对 → 场景法 → 状态迁移 → 错误推测/探索性。
> 附完整实例、方法组合决策树、评审清单与练习题。

---

## 一、方法体系总览

| 方法 | 解决什么问题 | 典型场景 | 覆盖率视角 |
| --- | --- | --- | --- |
| 等价类划分 | 输入域太大不能穷举 | 任何输入校验 | 每个等价类至少一次 |
| 边界值分析 | 边界附近最易出错 | 数值/长度/时间边界 | 上点、内点、离点 |
| 判定表 | 多条件组合的业务规则 | 优惠、风控、审批 | 每条规则至少一次 |
| 因果图 | 条件间有逻辑约束 | 复杂校验、联动 | 等价于判定表 |
| 正交/成对 | 参数组合爆炸 | 配置平台、多因子 | 两两组合覆盖 |
| 场景法 | 业务流程与分支 | 下单、支付、审批流 | 基本流+备选流+异常流 |
| 状态迁移 | 状态机系统 | 订单、工单、账号 | 状态/迁移/路径覆盖 |
| 错误推测 | 经验补充 | 高风险模块 | 依赖经验 |
| 探索性测试 | 未预期问题 | 迭代探索 | 会话式覆盖 |

**方法组合决策树：**

```
输入校验类 ──┬─ 有取值范围 → 等价类 + 边界值
             └─ 多字段组合 → 成对组合（pairwise）
业务规则类 ──┬─ 条件 ≤ 4 个 → 判定表
             └─ 条件多且有约束 → 因果图
流程状态类 ─── 场景法 + 状态迁移
高风险/复杂 ── 错误推测 + 探索性 + 安全测试
```

## 二、等价类划分

**定义**：把输入域划分成若干子集（等价类），同一子集中任意值对系统行为等价，只需选代表值。

**步骤**：

1. 分析每个输入条件的取值形态；
2. 划分有效等价类（合法）与无效等价类（非法）；
3. 为每个等价类取代表值；**每个无效等价类单独一条用例**（避免屏蔽），有效等价类可合并。

**示例：年龄 0~120 的注册**：

| 输入条件 | 有效等价类 | 无效等价类 |
| --- | --- | --- |
| 年龄 | 0–120 整数（如 25） | `<0`；`>120`；非整数（3.5）；非数字（abc）；空值 |
| 手机号 | 1[3-9] 开头 11 位 | 少于 11 位；非数字；非 1 开头；空 |

**常见错误：**

- 有效与无效混在一条用例里（无效被屏蔽，测不出问题）；
- 等价类有重叠或遗漏；
- 忘记"空/Null/空格"也是独立等价类。

> 补充：等价类不仅要看输入，还要看**输出等价类**（如金额区间对应的费率档位）。

## 三、边界值分析

**核心**：错误最常出现在边界（`<` vs `<=`、循环起止、数组下标、字符串长度、时间边界）。

**取点规则**（范围 [min, max]）：

| 点 | 值 | 说明 |
| --- | --- | --- |
| 上点 | min、max | 边界本身 |
| 内点 | min+1、max-1、中间值 | 范围内 |
| 离点 | min-1、max+1 | 刚越界 |

**示例：** 长度 6–20 的密码 → 5、6、7、13、19、20、21。

**边界类型清单：**

| 类型 | 例子 |
| --- | --- |
| 数值边界 | 0、-1、最大值、溢出值 |
| 长度边界 | 空串、1 字符、上限、上限+1 |
| 集合边界 | 空数组、单元素、超大数据集 |
| 时间边界 | 跨天/跨月/闰年、时区、夏令时、23:59:59、0:00:00 |
| 金额边界 | 0.01、限额、精度 0.1+0.2 |
| 分页边界 | page=0/1/末页/末页+1 |
| 状态边界 | 最后一次重试、最后一次错误密码 |

**输出边界**同样重要：如"满 100 减 10"规则，输入 99.99/100/100.01 验证优惠档位切换。

## 四、判定表法

**组成**：条件桩（输入条件）+ 动作桩（输出动作）+ 条件项（取值）+ 动作项（是否执行）。

**完整示例：电商优惠券使用规则**

- C1：订单金额 ≥ 100？
- C2：是否会员？
- C3：是否指定品类？
- C4：优惠券在有效期内？

**判定表（合并前 2⁴ = 16 条，等价合并后）：**

| 规则 | R1 | R2 | R3 | R4 | R5 | R6 |
| --- | --- | --- | --- | --- | --- | --- |
| C1 金额≥100 | Y | Y | Y | Y | N | — |
| C2 会员 | Y | Y | N | N | — | N |
| C3 指定品类 | Y | N | Y | N | — | Y |
| C4 有效期内 | Y | Y | Y | Y | Y | N |
| A1 可用 | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |
| A2 提示原因 | — | — | — | 品类不符 | 金额不够 | 券已过期 |

**技巧：**

- 先列全组合，再合并"无关条件"（用 `—` 表示 don't care）；
- 规则数 = 2^条件数，条件超过 5 个时用因果图/正交简化；
- 每条规则至少一条用例，高风险规则加边界。

## 五、因果图法

**流程**：分析原因（输入）与结果（输出）→ 标注约束 → 画因果图 → 转判定表 → 生成用例。

**四种基本关系**：与（∧）、或（∨）、非（¬）。

**五种约束：**

| 约束 | 含义 |
| --- | --- |
| E（互斥） | 最多一个成立（如同一个字段不能既是 A 又是 B） |
| I（包含） | 至少一个成立 |
| O（唯一） | 有且仅有一个成立 |
| R（要求） | a 成立则 b 必须成立 |
| M（屏蔽） | a 成立则 b 必不成立 |

**示例：** 登录校验

- C1：用户名正确（Y/N）
- C2：密码正确（Y/N）
- E1：用户名为空且密码为空（约束：二者不能同时为"空错误" → 只提示一个）
- 结果：E1 登录成功；E2 用户名或密码错误；E3 参数错误

> 面试提醒：因果图本质是"判定表的前置分析工具"，实际工作中可以跳过画图直接列判定表，但要说出约束思维。

## 六、正交实验与成对组合（Pairwise）

**问题**：4 个参数各 3 个取值 = 81 种组合，全测不可行。

**成对组合（Pairwise）原理**：绝大多数缺陷由**任意两个参数的交互**触发，保证所有参数两两组合至少出现一次即可。

**示例**：浏览器（Chrome/Firefox/Safari）× 系统（Win/macOS/Android）× 网络（4G/WiFi）× 语言（中/英）

- 全组合：3×3×2×2 = 36 条；
- Pairwise 约 12 条即可覆盖所有两两组合。

**工具：** PICT（微软）、AllPairs、在线 pairwise 生成器。

**使用建议：**

- 参数间相互独立时效果最好；
- 有强约束（如 iOS 不搭配某些机型）时先剪枝；
- Pairwise 后用高风险组合 + 边界值补充。

## 七、场景法

**三要素：**

- **基本流**：最顺畅的主流程；
- **备选流**：由基本流分支出的其他成功路径；
- **异常流**：出错路径与中断。

**完整示例：ATM 取款**

```
基本流：插卡 → 输密码 → 选择取款 → 输入金额 → 出钞 → 退卡
备选流：
  A1 密码错误 → 重试（限 3 次）
  A2 余额不足 → 提示 → 重新输入
  A3 超出单次限额 → 提示 → 重新输入
异常流：
  E1 卡片被吞
  E2 出钞失败（余额已扣）→ 冲正
  E3 网络中断 → 交易状态未知 → 查询确认
  E4 操作超时 → 退卡
```

**场景矩阵（用例表）：**

| 场景 | 基本流 | A1 | A2 | A3 | E2 | E4 | 预期 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| S1 | ✅ | | | | | | 取款成功 |
| S2 | | ✅ | | | | | 3 次锁定 |
| S3 | | | ✅ | | | | 提示余额不足 |
| S4 | ✅ | | | | ✅ | | 冲正，钱不丢 |
| S5 | | | | | | ✅ | 超时退卡 |

**要点：** 每条场景都是"一条完整链路"，覆盖异常后系统能否自愈与数据一致。

## 八、状态迁移测试

**步骤**：画状态迁移图 → 列状态表 → 设计覆盖用例。

**覆盖级别：**

| 级别 | 含义 | 用例量 |
| --- | --- | --- |
| 状态覆盖 | 每个状态至少到达一次 | 少 |
| 0-switch | 每条合法迁移至少走一次 | 中 |
| 1-switch | 连续两条迁移的所有组合 | 多（用工具生成） |
| 非法迁移 | 每条非法迁移都要验证被拒绝 | 必做 |

**示例：订单状态机**

```
待支付 ──支付成功──→ 已支付 ──发货──→ 已发货 ──确认收货──→ 已完成
   │                    │                │
   ├─超时/取消──→ 已取消  ├─退款成功──→ 已退款
   │                    └──────────────→ 退款中 ──→ 已退款
```

**用例设计：**

- 合法路径：待支付→已支付→已发货→已完成；
- 分支路径：待支付→已取消；已支付→退款中→已退款；
- 非法迁移：已完成→取消、已退款→发货、已取消→支付；
- 并发迁移：支付回调与用户取消同时到达（状态机加锁/乐观锁）；
- 时间迁移：超时自动取消的边界（29:59 vs 30:01）。

## 九、错误推测与探索性测试

### 9.1 错误推测清单（按经验）

- 空值、空格、null、undefined；
- 超长、超大、超深；
- 特殊字符、emoji、全角、换行；
- 重复提交、并发、乱序；
- 网络中断、超时、弱网、切后台；
- 权限边界、多角色、多租户；
- 时间相关：跨天、时区、闰年；
- 数值：0、负数、溢出、精度；
- 历史缺陷高发模块（看 Bug 库）。

### 9.2 会话式探索性测试（SBTM）

每个会话 60–120 分钟，围绕一个"测试章程"（Charter）：

```
探索：购物车结算
目标：发现金额计算与库存相关的缺陷
关注：优惠叠加、并发修改、失效商品
时间盒：90 分钟
产出：缺陷列表 + 覆盖区域记录 + 新风险点
```

**与用例测试的关系：** 用例保证"已知该测的"，探索性补"没想到的"。

## 十、从需求到用例的完整流程

```
1. 需求分析
   ├─ 功能点拆解：输入/处理/输出
   ├─ 明确规则与异常：状态、权限、边界
   └─ 非功能提取：性能、安全、兼容、可用性
2. 风险与优先级
   └─ 业务价值 × 变更影响 × 出错概率 → P0-P3
3. 维度展开（八维）
   功能｜界面交互｜异常容错｜性能并发｜安全｜兼容｜数据｜可用性
4. 方法选择（见决策树）
5. 用例编写（模板 + 参数化）
6. 评审
   └─ 完整性、独立性、可执行性、无冗余
7. 执行与维护
   └─ 缺陷反哺、用例更新、自动化沉淀
```

## 十一、完整实例：用户注册功能

**需求**：手机号 + 验证码 + 密码注册，成功后进首页；60 秒内可重发验证码；密码 8–20 位且含字母数字。

| 维度 | 设计 |
| --- | --- |
| 输入校验 | 手机号等价类+边界（11 位/10 位/非数字/非 1 开头）；密码长度 7/8/9/19/20/21、复杂度（纯数字/纯字母/字母数字/含特殊字符）、空值 |
| 逻辑规则 | 判定表：手机号格式 × 验证码正确 × 验证码未过期 × 密码合规 |
| 流程状态 | 状态迁移：未发送→已发送→已校验→注册成功→登录；验证码过期、重复注册、注册后 Token 有效期 |
| 异常 | 网络中断、验证码服务超时、并发同手机号注册、短信轰炸限流 |
| 安全 | 验证码绕过（万能码/复用/爆破）、密码弱口令、SQL 注入、敏感信息回显 |
| 性能 | 并发注册、验证码发送频率限制（60s/24h 上限） |
| 兼容 | H5/App/小程序一致性；不同运营商短信延迟 |

**方法落地：**

- 等价类+边界 → 手机号与密码；
- 判定表 → 四条件组合（16 条 → 合并）；
- 状态迁移 → 验证码生命周期与注册流程；
- 场景法 → 注册成功、验证码错误重试、重复注册；
- 错误推测 → 注入、超发、并发。

## 十二、用例评审与优先级

**评审检查清单：**

- [ ] 需求点全覆盖，能双向追溯；
- [ ] 正向/异常/边界/权限/数据/并发都有；
- [ ] 每条用例独立可执行、可重复；
- [ ] 预期结果明确、可验证（避免"正常显示"）；
- [ ] 无冗余（合并等价用例）；
- [ ] 高风险点有针对性用例；
- [ ] 可自动化标记清晰。

**优先级原则：**

| 优先级 | 判定 | 示例 |
| --- | --- | --- |
| P0 | 主流程/资损/安全 | 支付成功、金额正确 |
| P1 | 核心异常/无绕行 | 密码错误锁定 |
| P2 | 一般异常/边界 | 超长输入提示 |
| P3 | 体验/文案 | 提示语措辞 |

## 十三、常见错误与避坑

1. 方法堆砌但不组合（应"判定表 + 边界值"配合）；
2. 只设计正常流程，异常流靠"想到再说"；
3. 无效等价类合并成一条用例（屏蔽效应）；
4. 判定表条件爆炸不化简；
5. Pairwise 取代一切（高风险组合仍需全测）；
6. 状态机漏非法迁移与并发迁移；
7. 用例预期写"成功""正确"（不可验证）；
8. 不标注前置数据与清理，导致不可重复执行。

## 十四、练习题（可先自测再看要点）

1. **登录框**（用户名 6–20 位，密码 8–16 位）→ 要点：等价类+边界+判定表（验证码）+错误推测；
2. **满减券**（满 100 减 10、满 200 减 30，会员再 9 折，不与特价商品同享）→ 要点：判定表（4 条件）+ 金额边界 99.99/200/200.01；
3. **订单状态机**（待支付/已支付/发货/完成/取消/退款）→ 要点：0-switch + 非法迁移 + 并发迁移；
4. **文件上传**（≤10MB，支持 jpg/png/pdf）→ 要点：边界 9.9M/10M/10.1M、双扩展名、伪装文件、路径穿越；
5. **搜索**（关键词 + 类目 + 价格区间 + 排序）→ 要点：Pairwise（4 因子）+ 空结果 + 特殊字符 + 深分页。

---

## 十五、总结

> 黑盒用例设计的功力 = **维度齐全（知道测什么）× 方法匹配（知道怎么测）× 风险排序（知道先测什么）**。
> 面试回答"怎么设计用例"时：先给维度框架，再给方法组合，最后用一条业务实例讲透。
