## 一、性能理论基础

### 1.1 核心指标

| 指标 | 定义 | 关注点 |
| --- | --- | --- |
| TPS | 每秒事务数（业务视角） | 支付 TPS 500 |
| QPS | 每秒请求数 | 查询接口、缓存 |
| RT | 响应时间：平均、P95、P99、最大 | **看长尾，不看平均** |
| 并发数 | 同时在处理的请求数 | 与 RT、TPS 的关系 |
| 错误率 | 失败请求占比 | 含超时、限流拒绝 |
| 吞吐量 | 单位时间处理数据量 | 大文件、消息场景 |
| 资源利用率 | CPU/内存/IO/网络/连接 | 水位与瓶颈 |

**为什么看 P95/P99？** 平均值掩盖长尾；用户体感由慢请求决定；SLA 通常约定 P95/P99。

### 1.2 三大黄金公式

```
Little's Law:        并发数 = TPS × 平均 RT
吞吐量公式:           TPS = 并发数 / 平均 RT
容量估算:            目标 TPS = 峰值 QPS × 冗余系数(1.5~2)
```

**示例**：目标 1000 TPS，RT 200ms → 并发数 = 1000 × 0.2 = 200。

### 1.3 性能曲线模型

```
TPS
 │        ┌──── 拐点（最佳容量）
 │      ╱
 │    ╱         ╲  过载区：TPS 下降，RT/错误率飙升
 │  ╱             ╲
 └──────────────────────→ 并发数
```

- **轻载区**：TPS 随并发线性上升；
- **线性区**：接近拐点，RT 缓慢上升；
- **过载区**：资源争抢，TPS 下降甚至雪崩。

性能测试的目标就是找拐点、验证安全水位、防止过载。

## 二、测试类型与适用场景

| 类型 | 目的 | 加压方式 | 关注 |
| --- | --- | --- | --- |
| 基准测试 | 单接口基线 | 固定小并发 | RT、TPS 基线 |
| 负载测试 | 预期负载验证 | 目标并发/平台期 | 是否达标 |
| 压力测试 | 找极限与拐点 | 阶梯递增 | 拐点、过载行为 |
| 稳定性测试 | 长稳找泄漏 | 70% 负载跑 24h–7d | 内存/句柄/GC 趋势 |
| 峰值测试 | 大促瞬时 | 尖峰模型 | 排队、限流、降级 |
| 全链路压测 | 端到端容量 | 混合场景 | 端到端瓶颈 |

## 三、性能需求分析与目标设定

**三类输入：**

1. **业务目标**：大促目标 GMV → 峰值订单量 → 核心接口 TPS；
2. **SLA**：P95 ≤ 200ms、成功率 ≥ 99.9%、可用率 99.99%；
3. **历史基线**：上个版本/大促的实际峰值与瓶颈。

**二八原则与峰值系数：**

```
日均 QPS × 峰值系数（3–10 倍，按业务） = 日常峰值
大促目标 = 历史大促峰值 × 增长系数（1.5–3 倍）
压测目标 = 大促目标 × 冗余系数（1.2–1.5）
```

**输出：性能测试方案**（目标、场景、模型、环境、数据、通过标准）。

## 四、场景建模（核心方法论）

### 4.1 四类模型

| 模型 | 内容 | 来源 |
| --- | --- | --- |
| 业务模型 | 哪些链路是核心 | 业务方 + 线上日志 |
| 流量模型 | 各接口调用比例、思考时间 | 生产日志分析 |
| 数据模型 | 用户/商品/订单的量与分布 | 生产数据采样 |
| 脚本模型 | 参数化、事务、断言 | 压测工具实现 |

### 4.2 混合场景比例示例（电商）

| 业务 | 占比 | 说明 |
| --- | --- | --- |
| 浏览商品 | 50% | 读多写少，缓存命中高 |
| 搜索 | 20% | 搜索服务压力 |
| 加购 | 10% | 写操作 |
| 下单 | 10% | 库存/订单/事务 |
| 支付 | 5% | 外部依赖（Mock） |
| 查询订单 | 5% | 读 |

**关键点：**

- 按真实比例混合，不是每个接口都打满；
- 思考时间（pacing）模拟真实用户节奏；
- 热点数据（热 key/热商品）单独建模，否则测不出真实瓶颈。

### 4.3 数据准备

- 数据量级贴近生产（用户数、商品数、订单数）；
- 分布贴近真实（活跃度、地区、金额分布）；
- 压测数据打标（便于清理与影子库隔离）；
- 缓存预热策略明确（冷启动 vs 预热后）。

## 五、工具选型与实施

### 5.1 工具对比

| 工具 | 语言 | 协议支持 | 分布式 | CI 友好 | 适用 |
| --- | --- | --- | --- | --- | --- |
| JMeter | Java | 多（HTTP/JDBC/MQ） | Master-Slave | 中 | 传统压测、复杂协议 |
| K6 | JS | HTTP/WS/gRPC | k6 cloud/分布式 | 强 | 工程化、云原生 |
| Locust | Python | 任意（可编程） | 原生分布式 | 强 | 定制逻辑、Python 栈 |
| wrk | C | HTTP | 否 | 中 | 单纯打 RPS |
| Gatling | Scala | 多 | 支持 | 强 | 高性能脚本 |

**选型原则：** 协议支持 > 脚本能力 > 分布式与 CI > 团队熟悉度。

### 5.2 K6 示例（含阈值与场景）

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    browse: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '2m', target: 100 },   // 爬坡
        { duration: '5m', target: 100 },   // 平台期
        { duration: '1m', target: 200 },   // 摸高
        { duration: '1m', target: 0 },
      ],
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<200', 'p(99)<500'],
    http_req_failed: ['rate<0.001'],
  },
};

export default function () {
  const login = http.post('https://api.example.com/login',
    JSON.stringify({ user: 'u1', pwd: 'p1' }),
    { headers: { 'Content-Type': 'application/json' } });
  check(login, { '登录成功': (r) => r.status === 200 });
  const token = login.json('token');

  const order = http.post('https://api.example.com/order',
    JSON.stringify({ skuId: '1001', count: 1 }),
    { headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` } });
  check(order, { '下单成功': (r) => r.status === 200 });

  sleep(Math.random() * 3 + 1);   // 思考时间 1–4s
}
```

### 5.3 JMeter 关键配置

- 线程组：Ultimate Thread Group（爬坡/平台/尖峰）；
- 参数化：CSV Data Set Config（账号/商品数据）；
- 关联：JSON Extractor（token/orderId）；
- 定时器：Constant Throughput Timer（目标 TPS 控制）；
- 断言：Response Assertion + JSON Assertion；
- 分布式：Master-Slave，注意发压机自身水位；
- 监控：Backend Listener → InfluxDB → Grafana。

**发压机自检：** CPU < 70%、网络带宽、端口耗尽（TIME_WAIT）、文件句柄。

## 六、监控体系（四层）

| 层 | 指标 | 工具 |
| --- | --- | --- |
| 前端/客户端 | 首屏、JS 错误、接口失败率 | RUM、Sentry |
| 网关/接入 | QPS、RT、4xx/5xx、限流次数 | Nginx/网关监控 |
| 应用 | CPU、内存、GC、线程池、连接池、错误率 | Prometheus + Grafana、APM |
| 中间件 | DB 慢查询/连接/锁；Redis 命中/大 key；MQ 积压 | 各中间件监控 |
| 链路 | 各服务耗时 Span | SkyWalking/Jaeger/Zipkin |
| 系统 | CPU/内存/磁盘 IO/网络 | Node Exporter |

**压测必须与监控同屏观察**：没有监控的压测只能得到"TPS 数字"，得不到"为什么"。

## 七、瓶颈定位手册（按层排查）

### 7.1 排查顺序

```
1. 发压侧：压测机瓶颈？脚本逻辑耗时？断言过重？
2. 网络：带宽、丢包、DNS、TIME_WAIT 堆积
3. 接入层：Nginx worker、连接数、限流阈值
4. 应用层：CPU（us/sy）、GC、线程池、连接池、锁、异步队列
5. 缓存：命中率、大 key、热 key、连接数
6. 数据库：慢 SQL、锁等待、连接数、IO、主从延迟
7. MQ：积压、消费速率
8. 下游：RT 与错误率、超时重试放大
```

### 7.2 常见现象 → 可能原因

| 现象 | 可能原因 |
| --- | --- |
| CPU us 高 | 计算密集、序列化、正则回溯、加密 |
| CPU sy 高 | 上下文切换、系统调用、网络包处理 |
| CPU 低但 TPS 上不去 | IO/锁/连接池/限流/下游阻塞 |
| GC 频繁/停顿长 | 分配速率高、堆小、缓存不合理 |
| 线程池队列满 | 下游慢、任务处理慢、池太小 |
| 连接池耗尽 | 慢 SQL、连接泄漏、池配置小 |
| TIME_WAIT 多 | 短连接、客户端未复用 |
| 磁盘 IO 高 | 日志刷盘、大表扫描、临时表 |
| 内存持续涨 | 泄漏、缓存无上限、大对象常驻 |

### 7.3 常用命令

```bash
# 系统
top -Hp <pid>; vmstat 1 5; iostat -x 1 5; sar -n DEV 1

# JVM
jstat -gcutil <pid> 1000          # GC 频率与耗时
jstack <pid> | grep -A 30 <hex>   # 线程栈定位热点
jmap -heap <pid>; jmap -dump:live,format=b,file=heap.bin <pid>
# Arthas: dashboard / thread / trace / profiler

# 数据库
SHOW PROCESSLIST; SHOW ENGINE INNODB STATUS;
EXPLAIN <sql>; 慢查询日志

# 网络
ss -s; ss -ant | awk '{print $1}' | sort | uniq -c
```

## 八、典型调优案例

### 案例 1：慢 SQL 导致 TPS 上不去

- 现象：应用 CPU 低、DB CPU 高、RT 2s+；
- 定位：慢查询日志发现订单列表走全表扫描；
- 优化：加联合索引 + 改写深分页（延迟关联）；
- 结果：RT 2s → 80ms，TPS 提升 8 倍。

### 案例 2：频繁 Full GC

- 现象：RT 周期性毛刺、GC 日志显示 Full GC 每秒一次；
- 定位：jmap + MAT 发现本地缓存无上限；
- 优化：缓存加容量与 TTL，堆参数调整；
- 结果：Full GC 小时级，RT 毛刺消失。

### 案例 3：连接池配置过小

- 现象：并发上升后大量获取连接超时；
- 定位：连接池 active 打满、DB 侧连接数远未到上限；
- 优化：连接池从 20 → 100，配合 DB 最大连接与慢查询治理；
- 结果：错误率归零，TPS 翻倍。

> 每个案例的面试讲法：现象 → 数据 → 假设 → 验证 → 优化 → 复测。

## 九、全链路压测

### 9.1 核心步骤

1. **明确链路**：绘制请求流转图，确定核心场景；
2. **准备环境**：贴近生产的规格与配置，第三方 Mock；
3. **数据隔离**：影子库/影子表、流量标识（forcebot）、独立环境；
4. **脚本编排**：链路 API 序列 + 参数化 + 思考时间；
5. **执行**：阶梯加压 → 平台期 → 摸高 → 峰值冲击；
6. **监控**：全链路指标 + 链路追踪；
7. **分析**：瓶颈定位 → 优化 → 复压验证；
8. **输出**：容量报告、扩容建议、风险清单。

### 9.2 隔离方案对比

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 影子库 | 压测流量写影子表 | 隔离彻底 | 成本高 |
| 流量标识 | 标识走 Mock/隔离逻辑 | 灵活 | 需业务改造 |
| 独立环境 | 全链路复制 | 简单 | 数据真实度差 |

### 9.3 架构示意

```
[压测工具集群] → [API 网关] → [微服务] → [DB/缓存/MQ]
       │              │            │
       ▼              ▼            ▼
 [压测指标收集] ← [Prometheus] ← [链路追踪 Agent]
       └────────────→ Grafana / SkyWalking 大盘
```


## 十二、常见误区

1. 只测接口不测链路（链路瓶颈在组合处）；
2. 只报 TPS 不看错误率（拒绝的请求也算"处理"）；
3. 用平均值判断性能（必须看 P95/P99）；
4. 压测数据全冷（缓存命中假象）；
5. 忽略思考时间与流量比例（脱离真实）；
6. 压测机先到瓶颈（发压端污染结果）；
7. 没有监控只靠猜（无法定位）；
8. 只压一次不回归（优化后必须复测）。

## 十三、面试问答

**Q1：性能测试怎么做？**
> 需求分析（目标/SLA）→ 场景建模（业务/流量/数据）→ 环境数据准备 → 工具实施（脚本、参数化）→ 阶梯执行 + 全链路监控 → 瓶颈定位 → 优化复测 → 报告与容量建议。

**Q2：TPS 上不去怎么排查？**
> 从发压侧到后端逐层：压测机水位 → 网络 → 网关限流 → 应用 CPU/GC/线程池/连接池 → 缓存 → DB 慢查询/锁 → MQ → 下游；用链路追踪定位最慢环节，再深入该层工具验证。

**Q3：怎么设计一个秒杀压测场景？**
> 峰值建模（开场瞬间流量）+ 库存热点 + 限流/队列 + 幂等；指标：秒杀成功率、超卖、排队时长、系统水位；配合降级与风控验证。

**Q4：性能测试什么时候介入？**
> 方案评审提风险 → 提测后接口基准 → 核心稳定后全链路 → 大促前峰值与长稳。

## 十四、总结

> 性能测试 = **建模（真实流量）× 执行（科学加压）× 监控（四层可见）× 定位（分层排查）× 调优（复测验证）**。
> 五字口诀：**模压监定调**（建模、压测、监控、定位、调优）。
