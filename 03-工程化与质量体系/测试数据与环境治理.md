# 🗂️ 测试数据与环境治理

> "测试环境又挂了""数据被谁改了""这个用例只能在我机器上跑"——
> 环境与数据是自动化稳定性的最大敌人。本篇给出系统化的治理方案。

---

## 一、测试数据为什么难

| 痛点 | 场景 |
| --- | --- |
| 不够 | 造数要跑完整链路，耗时耗力 |
| 不对 | 边界、异常数据难以构造 |
| 不稳 | 数据被并发用例/他人修改 |
| 不净 | 用完不清理，环境越来越脏 |
| 不安全 | 生产数据未脱敏就进测试环境 |
| 不一致 | 多系统间数据关联不上（用户 ID 对不齐） |

---

## 二、数据准备六种方式

| 方式 | 说明 | 适用 | 风险 |
| --- | --- | --- | --- |
| 手工 UI 操作 | 页面点击创建 | 少量、探索性 | 慢、重复 |
| SQL 直插 | 直接写库 | 单表、简单数据 | 绕过业务逻辑，字段易漏 |
| 调用 API | 走系统接口创建 | 端到端、推荐 | 依赖服务可用 |
| 造数平台 | 模板化 + 编排 | 规模化、自助 | 建设成本 |
| 流量回放 | 复用真实流量参数 | 高保真 | 需处理写流量 |
| 生产脱敏 | 导出 + 脱敏 | 大规模真实分布 | 合规、安全审批 |

**选择原则：**

```
优先 API（真实）> 造数平台（效率）> SQL（快速）> 手工（兜底）
禁止：未脱敏生产数据进测试环境
```

## 三、数据隔离策略

### 3.1 隔离级别

| 级别 | 方案 | 隔离度 | 成本 |
| --- | --- | --- | --- |
| 团队隔离 | 每团队独立环境/库 | 高 | 高 |
| 用例隔离 | 每条用例独立数据（唯一前缀） | 中 | 低 |
| 用户隔离 | 按测试账号划分数据空间 | 中 | 中 |
| 影子库 | 压测/回放流量写影子表 | 高 | 高 |
| 快照回滚 | 执行前快照，执行后恢复 | 高 | 存储成本 |

### 3.2 用例级数据隔离（最常用）

```python
import uuid

@pytest.fixture
def unique_user(api_client):
    """每条用例创建独立的用户，避免数据冲突"""
    suffix = uuid.uuid4().hex[:8]
    user = api_client.create_user(
        username=f"autotest_{suffix}",
        email=f"autotest_{suffix}@test.local",
    )
    yield user
    api_client.delete_user(user["id"])   # 清理，保证可重复执行
```

**要点：**

- 数据带唯一前缀（如 `autotest_`），便于识别和批量清理；
- 用例不依赖"环境里已存在的数据"；
- 清理放 teardown，且清理失败不影响用例结果（记录日志 + 定时补偿清理）。

### 3.3 幂等造数

```sql
-- 幂等插入：存在则更新（MySQL）
INSERT INTO test_account (id, name, balance)
VALUES (1001, 'autotest_account', 1000.00)
```

```python
def ensure_user(api_client, username):
    """不存在则创建，存在则返回，保证可重复调用"""
    user = api_client.find_user(username)
    return user or api_client.create_user(username)
```

## 四、数据工厂设计

### 4.1 能力清单

```
1. 数据模板：字段 + 生成规则（随机/枚举/引用/函数）
2. 关联构造：按外键依赖顺序创建（用户 → 订单 → 支付）
3. 批量生成：支持大数据量（压测数据）
4. 数据池：生成后存储、分配、归还、销毁
5. 对外接口：供自动化框架/压测/功能测试调用
6. 环境路由：自动指向对应环境的数据源
7. 回收策略：TTL、引用计数、手动清理
```

### 4.2 代码示例：链式数据构造

```python
class DataFactory:
    def __init__(self, api_client, db):
        self.api = api_client
        self.db = db

    def create_user_with_order(self, order_count=1):
        user = self.api.create_user(f"autotest_{uuid.uuid4().hex[:6]}")
        orders = [self.api.create_order(user["id"]) for _ in range(order_count)]
        return {"user": user, "orders": orders}

    def cleanup(self, bundle):
        for order in bundle.get("orders", []):
            self.api.cancel_order(order["id"])
        if bundle.get("user"):
            self.api.delete_user(bundle["user"]["id"])
```

## 五、环境治理

### 5.1 环境分层

```
本地(local) → 开发(dev) → 联调(test) → 预发(staging) → 生产(prod)
```

| 环境 | 用途 | 特点 |
| --- | --- | --- |
| dev | 开发自测 | 不稳定、数据随意 |
| test | 测试主战场 | 多人共用、最易冲突 |
| staging | 上线前验证 | 配置接近生产 |
| prod | 生产 | 只读验证、灰度 |

### 5.2 六大常见问题与治理

| 问题 | 根因 | 治理方案 |
| --- | --- | --- |
| 环境被随意重启 | 无责任人、无发布规范 | 环境负责人制 + 变更窗口 + 通知机制 |
| 服务版本不一致 | 手工部署 | IaC/Helm 版本化部署 |
| 配置漂移 | 手工改配置 | 配置中心 + 版本管理 + 审计 |
| 依赖服务不稳定 | 第三方/其他团队 | Mock/服务虚拟化 |
| 数据互相覆盖 | 共用一套数据 | 数据隔离 + 唯一前缀 |
| 环境不可用无感知 | 无监控 | 环境健康检查 + 告警 + 状态页 |

### 5.3 环境健康检查脚本

```bash
#!/usr/bin/env bash
# 环境巡检：核心服务存活 + 数据库连通 + 关键接口
set -euo pipefail

SERVICES=("http://app.test.local/health" "http://pay.test.local/health")
FAILED=0
for url in "${SERVICES[@]}"; do
  code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 "$url" || true)
  if [[ "$code" != "200" ]]; then
    echo "❌ $url 返回 $code"
    FAILED=1
  else
    echo "✅ $url OK"
  fi
done

# 数据库连通性
mysqladmin ping -h mysql.test.local -u test -p"$DB_PASS" --silent \
  || { echo "❌ MySQL 不可用"; FAILED=1; }

exit $FAILED
```

### 5.4 动态测试环境（云原生方案）

```
MR 提交 → CI 触发 → Helm 部署独立 Namespace（app-mr-1234）
→ 数据源指向独立 schema（或影子表）
→ 跑自动化用例 → 结果上报 → 销毁环境（TTL 兜底）
```

**收益：** 环境按需、互不干扰、用完即毁；**难点：** 依赖服务（DB/MQ/Redis）的隔离与成本。

## 七、面试真题

### Q1：接口测试的数据依赖怎么解决？

- 优先用例自建数据（API 造数 + teardown 清理）；
- 跨系统依赖用造数平台或 Mock；
- 环境预置基础数据（字典、配置）用幂等脚本保障；
- 禁止依赖"别人创建的数据"和"执行顺序"。

### Q2：测试数据被污染，用例时好时坏怎么办？

1. 数据加唯一前缀，按用例隔离；
2. 失败时先检查数据前置条件（不要只看业务断言）；
3. 执行前 ensure（幂等构造），执行后清理；
4. 环境层做定时数据重置；
5. 用数据工厂统一管理，禁止散落 SQL。

### Q3：如何做大规模压测数据准备？

- 模板 + 批量生成（如 100 万用户、1000 万订单）；
- 直连数据库批量导入（注意索引、事务批次）；
- 数据分布贴近真实（活跃度、地区、金额分布）；
- 压测数据打标，便于清理和隔离（影子库/影子表）。

### Q4：多环境配置怎么管理？

环境配置与代码分离（配置文件/配置中心），启动时按环境注入；敏感信息走密钥管理；禁止在用例中硬编码 URL 和账号。

### Q5：怎么保证自动化用例可重复执行？

数据幂等 + 状态自愈 + 清理彻底 + 不依赖外部状态 + 执行顺序无关。

---

## 八、总结

> 环境与数据治理的目标：**任何人在任何时间、任何执行顺序下，用例都能稳定通过。**
> 手段：唯一化前缀、幂等构造、自动清理、环境健康检查、配置版本化。
